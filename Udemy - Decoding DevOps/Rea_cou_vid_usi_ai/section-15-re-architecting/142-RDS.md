# 🧠 SECTION 1: THEORY (DEEP LEARNING MODE)

## 1.1 Why Amazon RDS for vprofile

The vprofile application requires a MySQL database. Rather than managing MySQL on a raw EC2 instance (as done in the lift-and-shift approach), this architecture uses **Amazon RDS** — a fully managed relational database service. RDS handles the underlying OS, patching, backups, and high-availability mechanics, letting you focus on the database itself. The specific engine for vprofile is **MySQL**, and the database that the application expects is called **`accounts`**. [\[142-rds \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/142-rds.txt)

***

## 1.2 Parameter Groups — Configuration Without SSH

One of the core constraints of Amazon RDS is that **you cannot SSH into the database instance**. There is no operating system-level access. This means you cannot edit MySQL configuration files (like `my.cnf`) directly. This is a fundamental trade-off of managed services — you surrender OS access in exchange for operational automation.

**Parameter groups** are how RDS solves this. A parameter group is a named collection of database engine configuration settings. Every RDS instance is associated with a parameter group. When you launch an RDS instance without specifying one, it uses the **default parameter group**, which contains AWS's standard defaults and **cannot be modified**. [\[142-rds \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/142-rds.txt)

To customize any configuration (buffer sizes, connection limits, character sets, timeouts, etc.), you must **create your own parameter group**, attach it to your instance, and modify the parameters within it. The instructor notes that in real-time environments, database administrators ("DB geeks") will need this full customization capability. The custom parameter group in this project is named `vprofile-rds-rearch-paragrp`. [\[142-rds \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/142-rds.txt)

When creating a parameter group, three selections are critical:

1. **Engine type** — must match the database engine you intend to launch (MySQL Community in this case)
2. **Parameter group family** — must match the engine version (MySQL 8.4 for this project)
3. **Type** — must be **DB Parameter Group**, not "Cluster Parameter Group." A cluster parameter group is for Aurora clusters or multi-node configurations. Since we are launching a **single RDS instance**, we need the DB-level type. [\[142-rds \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/142-rds.txt)

Once created, the parameter group exposes an enormous number of configurable settings (approximately 27 pages worth). You don't need to understand all of them, but the key mental model is: **whenever you have a configuration change requirement for your RDS instance, the parameter group is where you find and modify that setting**. [\[142-rds \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/142-rds.txt)

🔍 **Deep Dive**: The parameter group acts as an **abstraction layer** between you and the database configuration file. In a self-managed MySQL on EC2, you would edit `/etc/my.cnf`. In RDS, you edit key-value pairs inside the parameter group, and RDS applies them to the underlying MySQL configuration internally. Some parameters require a reboot to take effect (static parameters), while others apply immediately (dynamic parameters).

## 1.3 Subnet Groups — Network Placement Control

Every RDS instance runs inside a VPC (Virtual Private Cloud) and must be placed in subnets within that VPC. A **DB subnet group** is a named collection of subnets (across multiple Availability Zones) that tells RDS which subnets it is allowed to use when placing the database instance. [\[142-rds \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/142-rds.txt)

Why does this exist? In real environments, database administrators need precise control over network placement. They may have created a dedicated VPC for database workloads, or specific private subnets with particular routing rules and NACLs. The subnet group lets you define exactly which subnets RDS can use without giving it blanket access to the entire VPC. [\[142-rds \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/142-rds.txt)

Each AWS region has a **default VPC** with **default subnets** (one per Availability Zone). For this project, the default VPC and all its subnets are used. The subnet group is named `vprofile-rds-rearch-subgrp`. When creating it, you select the VPC first, then the Availability Zones, and finally the specific subnets within those zones. One zone can contain multiple subnets. [\[142-rds \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/142-rds.txt)

The instructor selects **all zones** and **all subnets** for simplicity but notes that in a real project, you might need to select specific subnet IDs based on your network architecture. [\[142-rds \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/142-rds.txt)

⚠️ **Expert Note**: When creating a subnet group, you might encounter an error that a specific zone or subnet is unavailable. This is an AWS capacity or service limitation in that AZ. The fix is straightforward — remove that specific zone/subnet from the selection and recreate. [\[142-rds \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/142-rds.txt)

## 1.4 RDS Instance Name vs. Database Name — A Critical Distinction

The instructor makes an explicit correction during the video to clarify a common confusion:

* **RDS instance name** = the name of the managed database service resource in AWS (e.g., `vprofile-rds-rearch`). This is what you see in the AWS console.
* **Database name** = the actual MySQL database created inside that RDS instance (e.g., `accounts`). This is what your application connects to.

These are two different things at two different layers. The RDS instance is the infrastructure; the database is the logical data container running inside that infrastructure. The vprofile application specifically requires a database named **`accounts`** — this is set in the "Additional configuration" section during RDS creation, not in the instance name field. [\[142-rds \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/142-rds.txt)

## 1.5 Template Selection — Cost and Configuration Control

RDS offers three templates when creating an instance:

| Template       | Behavior                                                                                 |
| -------------- | ---------------------------------------------------------------------------------------- |
| **Production** | Creates a Multi-AZ database cluster — high availability but significantly more expensive |
| **Dev/Test**   | Full configuration visibility, all options available, but no forced HA settings          |
| **Sandbox**    | Locks everything to free-tier options; grays out production features like Multi-AZ       |

The instructor selects **Dev/Test** because it provides full visibility into all configuration options (which is valuable for learning) while still allowing you to manually choose the most cost-efficient (free-tier) settings. **Production must be avoided** in a learning context because it defaults to Multi-AZ which incurs real charges. If you want zero risk of unexpected charges, **Sandbox** is the safest choice — it forces free-tier settings automatically. [\[142-rds \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/142-rds.txt)

After selecting Dev/Test, you must explicitly choose **Single-AZ database** (not Multi-AZ) to avoid cost. [\[142-rds \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/142-rds.txt)

## 1.6 Engine Version Selection

The MySQL engine version must be **8.4.x**. The instructor has tested compatibility with the vprofile application up to version 8.4.8. The minor version (the `.8` part) can vary, but the major family **must remain 8.4** until the lecture is updated. This is important because MySQL version differences can introduce breaking changes in SQL syntax, authentication mechanisms, or default configurations that would break the application. ## 1.7 Credential Management

RDS provides two credential management approaches:

1. **Self-managed** — you generate and store the password yourself
2. **AWS Secrets Manager** — AWS stores and rotates the password automatically (this is a paid service)

For this project, **self-managed** is used because Secrets Manager is not free. The password is **auto-generated** by clicking the auto-generate option. The username is `admin`. [\[142-rds \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/142-rds.txt)

**Critical operational detail**: After clicking "Create database," you must **immediately click "View connection details"** to copy the auto-generated password. If you miss this step, the password is not retrievable later through the console. The instructor emphasizes saving this password somewhere (like a sticky note) because the vprofile application needs it to authenticate to the RDS instance. [\[142-rds \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/142-rds.txt)

## 1.8 Instance Configuration — Compute Sizing

RDS instances come in different classes:

* **Standard** / **Memory-optimized** — for production workloads with many concurrent users, requiring high EBS bandwidth, RAM, and CPU
* **Burstable** — for development, testing, and light workloads

For this project, **burstable class** is selected, specifically **db.t3.micro** or **db.t2.micro** — both with **1 GB RAM**. The key verification is ensuring the instance shows 1 GB RAM, confirming you're on the free-tier-eligible size. [\[142-rds \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/142-rds.txt)

## 1.9 Storage Configuration

The storage settings involve three decisions:

1. **Storage type**: **GP3** (General Purpose SSD) — cost-efficient for this use case. Provisioned IOPS (io1/io2) is faster but more expensive and unnecessary here. [\[142-rds \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/142-rds.txt)

2. **Allocated storage**: Must be reduced to **20 GB**. The Dev/Test template defaults to 200 GB — this is a trap for cost if you don't change it. If you selected the Sandbox template, it defaults to 20 GB automatically. [\[142-rds \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/142-rds.txt)

3. **Storage auto-scaling**: The instructor recommends **unchecking** this for safety, even though it wouldn't actually trigger since no significant data is being added. This feature automatically increases storage when a threshold is exceeded. In a learning environment, disabling it removes any risk of unexpected storage expansion. [\[142-rds \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/142-rds.txt)

## 1.10 Connectivity — Network and Security

The connectivity configuration determines how the RDS instance is reachable:

* **VPC**: Default VPC (or your project-specific VPC in real environments)
* **DB Subnet Group**: The custom subnet group created earlier (`vprofile-rds-rearch-subgrp`) must be selected here. This is where the prerequisite work pays off. [\[142-rds \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/142-rds.txt)
* **Public access**: **Not required**. The vprofile application connects to RDS **privately within the AWS network**. "Public access" in this context means accessibility from the internet — which is unnecessary and a security risk for a database. [\[142-rds \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/142-rds.txt)
* **Security group**: The **default security group must be removed** and replaced with the **vprofile backend security group**. RDS, being a backend service, follows the same security group placement rule as the other backend services (Memcache, RabbitMQ in the earlier EC2 lecture). All backend services share the same security group. [\[142-rds \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/142-rds.txt)
* **Port**: **3306** — the MySQL default. No change needed. [\[142-rds \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/142-rds.txt)

```

## Subnet Group — Mental Model

```
Problem: DBAs need network placement control
Solution: Subnet Group = allowed-subnets whitelist for RDS

VPC → Availability Zones → Subnets

## Reusable Engineering Patterns

```
1. ABSTRACTED CONFIGURATION
   No direct file access → parameter-based config layer
   Pattern: managed service replaces file-level control with API/UI parameters

2. NETWORK PLACEMENT CONTROL
   Subnet group = declarative network constraint
   Pattern: define allowed placement zones before resource creation

3. PREREQUISITE-THEN-RESOURCE
   Create config objects (PG, subnet group) BEFORE the main resource
   Pattern: dependencies must exist before the dependent resource

4. CREDENTIAL CAPTURE WINDOW
   Auto-generated secrets shown once → must capture immediately
   Pattern: ephemeral credential display in managed services

5. SAME-TRUST-ZONE BACKEND
   All backend services (EC2 or managed) → same security group
   Pattern: service role determines network zone, not service type

6. PARALLEL PROVISIONING
   RDS takes time → start next service (ElastiCache) while waiting
   Pattern: overlap long-running provisions to reduce total setup time
```
