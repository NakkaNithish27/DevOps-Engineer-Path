## 1.1 What We Are Generating and Why

In the previous lectures, all Kubernetes manifests were written manually in the `kubedefs` folder — deployments, services, PVC, secret, ingress. These work, but they are **static**. Every time you need to change an image name, a tag, a port, or a replica count, you must edit the YAML files directly. In a CI/CD pipeline, this is impractical — the pipeline needs to programmatically update values (especially image names and tags) after every build. [\[365-helm-c...rts-part-2 \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/365-helm-charts-part-2.txt)

A **Helm chart** solves this by **parameterizing** the manifests. Instead of hardcoded values, the templates use variables (e.g., `{{ .Values.app.image }}`). All variable values live in a single `values.yaml` file. The CI/CD pipeline updates `values.yaml` — changing the image tag to the latest build — and Helm renders the templates with the new values. The instructor states: "This is what will be updated automatically from our continuous integration pipeline." [\[365-helm-c...rts-part-2 \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/365-helm-charts-part-2.txt)

## 1.3 The Prompt — Anatomy and Engineering Decisions

The prompt ([365.PromptHelmCharts.txt](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/365.PromptHelmCharts.txt?EntityRepresentationId=cacfb451-75e7-466b-9a2c-6220eaab5bc2)) encodes every architectural decision for the Helm chart. Each line represents a deliberate requirement: [\[365.PromptHelmCharts \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/365.PromptHelmCharts.txt)

### Chart Structure

**Chart name: `vprofile`**, placed in `helm/vprofile/`. The `helm/` parent folder separates Helm artifacts from application source code and Kubernetes manifests. [\[365.PromptHelmCharts \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/365.PromptHelmCharts.txt)

**Separate template files per resource type:** `app-deployment.yaml`, `db-deployment.yaml`, `mc-deployment.yaml`, `rmq-deployment.yaml`, `services.yaml`, `ingress.yaml`, `secret.yaml`, `pvc.yaml`, `dockerregistry-secret.yaml`. The instructor explains: "This is good for management." One giant template file would be unmaintainable. Each file corresponds to a logical resource. [\[365-helm-c...rts-part-2 \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/365-helm-charts-part-2.txt)

### values.yaml Design

**Separate variable sections** for `app`, `db`, `memcached`, `rabbitmq`, `initcontainers`, `ingress`, `secrets`, `dockerregistry`. **One level nesting only** — meaning `app.image`, `app.tag`, `app.replicas`, not `app.container.image.name`. This keeps the values file flat enough for easy CI/CD manipulation. [\[365.PromptHelmCharts \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/365.PromptHelmCharts.txt), [\[365-helm-c...rts-part-2 \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/365-helm-charts-part-2.txt)

The instructor shows the structure:

```yaml
app:
  image: <image-name>
  tag: latest
  replicas: 1
  containerPort: 8080
```

And in the template: `{{ .Values.app.image }}:{{ .Values.app.tag }}`. The image name and tag are **separate variables** — the prompt explicitly requires this because Copilot sometimes combines them into one field, which breaks CI/CD pipelines that update only the tag. [\[365-helm-c...rts-part-2 \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/365-helm-charts-part-2.txt)

### Image Tags

**All image tags must default to `latest`** — no empty tag values. The prompt states: "Sometimes it gives empty tags so I've given here that no empty tag values, there should be some tag, otherwise the Helm chart will fail." An empty tag in a Kubernetes image reference causes pull failures. [\[365-helm-c...rts-part-2 \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/365-helm-charts-part-2.txt)

### Storage

**`db.storageClass` must be `gp2`** for AWS EKS. In the original `kubedefs` manifests, the PVC used `storageClassName: default`. But on an EKS cluster, the appropriate storage class for EBS volumes is `gp2`. The Helm chart's values file overrides this. `db.storageSize` is `3Gi`. [\[365-helm-c...rts-part-2 \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/365-helm-charts-part-2.txt)

## 1.4 AWS ALB Controller — Why Not NGINX Ingress

In the previous Kubernetes deployment (lecture 359), the NGINX Ingress Controller was used, which created an NLB. For this EKS-based deployment, the project switches to the **AWS ALB Controller** (Application Load Balancer Controller). This is a different ingress controller that creates **AWS Application Load Balancers** natively. [\[365-helm-c...rts-part-2 \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/365-helm-charts-part-2.txt)

To use the ALB Controller, the Ingress manifest needs specific **annotations**: [\[365.PromptHelmCharts \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/365.PromptHelmCharts.txt)

| Annotation                                   | Value                         | Purpose                                      |
| -------------------------------------------- | ----------------------------- | -------------------------------------------- |
| `kubernetes.io/ingress.class`                | `alb`                         | Tells K8s to use the ALB controller          |
| `alb.ingress.kubernetes.io/scheme`           | `internet-facing`             | Makes the ALB publicly accessible            |
| `alb.ingress.kubernetes.io/target-type`      | `ip`                          | Routes directly to Pod IPs                   |
| `alb.ingress.kubernetes.io/certificate-arn`  | `<Your ARN>`                  | SSL certificate from AWS Certificate Manager |
| `alb.ingress.kubernetes.io/listen-ports`     | `[{"HTTP":80},{"HTTPS":443}]` | Listen on both 80 and 443                    |
| `alb.ingress.kubernetes.io/ssl-redirect`     | `443`                         | Redirect HTTP to HTTPS                       |
| `alb.ingress.kubernetes.io/backend-protocol` | `HTTP`                        | Backend (Tomcat) speaks HTTP, not HTTPS      |

The instructor emphasizes: these annotations are **project-specific**, not Helm-specific. "The real-time project you're working on might be using a different controller, so you need to give that kind of information over here." You need to understand your project's infrastructure requirements — which controller, which scheme, which target type — and encode them in the Ingress annotations. [\[365-helm-c...rts-part-2 \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/365-helm-charts-part-2.txt)

The **certificate ARN** comes from AWS Certificate Manager. If you have a domain and created a public certificate (verified through DNS validation), you copy its ARN and paste it into the annotation. This enables HTTPS access through the ALB with your domain's certificate. [\[365-helm-c...rts-part-2 \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/365-helm-charts-part-2.txt)

⚠️ **Expert Note**
The `backend-protocol: HTTP` annotation is important. The Tomcat application listens on HTTP (port 8080), not HTTPS. If this were set to `HTTPS`, the ALB would try to establish an HTTPS connection to the Pod, which would fail because Tomcat doesn't have SSL configured. SSL termination happens at the ALB — the ALB handles HTTPS from the user, then communicates with the backend over plain HTTP. [\[365-helm-c...rts-part-2 \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/365-helm-charts-part-2.txt)

## 1.5 Conditional Docker Registry Secret

The prompt includes a **conditional rendering** pattern for the Docker registry secret. The `dockerregistry.enabled` flag in `values.yaml` defaults to `false`. When `false`, the Docker registry secret is not created, and `imagePullSecrets` is not added to the app and db deployments. When set to `true`, the secret is created and `imagePullSecrets` is included. [\[365.PromptHelmCharts \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/365.PromptHelmCharts.txt)

This is needed when using **private Docker Hub repositories**. If your images are public, you don't need registry credentials — keep `enabled: false`. If private, set `enabled: true` and provide the `server`, `username`, `password`, and `email` in `values.yaml`. [\[365.PromptHelmCharts \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/365.PromptHelmCharts.txt)

The `imagePullSecrets` is only added to **app and db deployments** (the ones with custom images), not to memcached or rabbitmq (which use official public images). [\[365.PromptHelmCharts \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/365.PromptHelmCharts.txt)

## 1.6 The values.yaml File — The CI/CD Interface

The `values.yaml` file is the **single interface** between the Helm chart and the CI/CD pipeline. The pipeline doesn't touch template files — it only modifies `values.yaml` (specifically `app.image` and `app.tag` after each build). Everything else in the values file is configured once during project setup. [\[365-helm-c...rts-part-2 \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/365-helm-charts-part-2.txt)

Key values to verify and configure:

* **`ingress.enabled`**: Must be set to `true` (defaults to `false` in the generated chart). Without this, no load balancer is created.
* **`ingress.host`**: Must be set to your actual domain (e.g., `vprofile.hkhinfotek.xyz`). If you don't have a domain, leave `example.com` and skip browser testing.
* **`db.storageClass`**: Must be `gp2` for AWS EKS.
* **All image tags**: Must have a value (default: `latest`), never empty. [\[365-helm-c...rts-part-2 \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/365-helm-charts-part-2.txt)

## 1.7 The Git Push — Connecting to Argo CD

After the Helm chart is generated and verified, it is committed and pushed to the `vprofile-helm` Git repository on the `main` branch. This repository is what **Argo CD** watches. When Argo CD detects changes in this repository (new image tag in `values.yaml`, for example), it automatically deploys the updated Helm chart to the Kubernetes cluster. The Git push is therefore the trigger for the GitOps deployment pipeline. [\[365-helm-c...rts-part-2 \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/365-helm-charts-part-2.txt)

## AWS ALB Ingress Annotations

```yaml
annotations:
  kubernetes.io/ingress.class: alb              ← use ALB controller
  alb.ingress.kubernetes.io/scheme: internet-facing  ← public ALB
  alb.ingress.kubernetes.io/target-type: ip      ← route to Pod IPs
  alb.ingress.kubernetes.io/certificate-arn: <ARN>   ← ACM certificate
  alb.ingress.kubernetes.io/listen-ports: '[{"HTTP":80},{"HTTPS":443}]'
  alb.ingress.kubernetes.io/ssl-redirect: '443'  ← force HTTPS
  alb.ingress.kubernetes.io/backend-protocol: HTTP   ← Tomcat speaks HTTP

spec:
  ingressClassName: alb                          ← NOT nginx

Certificate ARN: AWS Console → Certificate Manager → copy ARN
```

## NGINX vs ALB Controller

```
Previous (kops cluster):     NGINX Ingress Controller → NLB
This (EKS cluster):          AWS ALB Controller → ALB

NGINX: ingressClassName: nginx, annotations: nginx.*
ALB:   ingressClassName: alb,   annotations: alb.*

Both create load balancers, but ALB is AWS-native
```

## Key Engineering Patterns

| Pattern                                    | Manifestation                                                                                          |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------ |
| **Parameterization for CI/CD**             | Static manifests → Helm templates with `values.yaml` — pipeline changes values, not templates          |
| **AI-assisted code generation**            | Iterative prompt refinement → consolidated prompt → verify → fallback to known-good code               |
| **One file per resource**                  | Template separation for management — each resource type independently editable                         |
| **Annotation-driven controller selection** | ALB vs NGINX determined by annotations, not by chart structure — same Ingress kind, different behavior |
| **Conditional rendering**                  | `dockerregistry.enabled` toggles secret + imagePullSecrets — feature flags in infrastructure           |
| **Environment-specific values**            | `storageClass: default` (kops) vs `gp2` (EKS) — Helm values absorb infrastructure differences          |
| **Git as deployment trigger**              | Push to main → Argo CD detects → deploys — GitOps pattern                                              |
