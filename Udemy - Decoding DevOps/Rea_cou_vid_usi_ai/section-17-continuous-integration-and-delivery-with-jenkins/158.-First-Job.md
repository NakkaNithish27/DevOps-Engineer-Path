# Deep Learning Material: Jenkins First Job

---

## 🧠 SECTION 1: THEORY (DEEP LEARNING MODE)

---

### What is a Jenkins Job?

A Jenkins **job** (also called an *item*) is the fundamental unit of work in Jenkins. Think of it as a container that holds a complete set of instructions telling Jenkins: *what to do, when to do it, where to get the code from, and what to do after the work is finished.* Everything in Jenkins revolves around jobs — they are the reason Jenkins exists as a CI/CD tool.

In the real world, a DevOps engineer's core responsibility is to automate repetitive processes: compiling code, running tests, packaging applications, and deploying them. Without Jenkins jobs, a developer or engineer would have to manually SSH into a server, run scripts, check results, and notify the team — every single time. That's error-prone and unscalable. Jenkins jobs replace all of that with a repeatable, auditable, automated unit of execution.

Internally, when Jenkins runs a job, it creates an isolated execution environment (called a **workspace**), runs the configured steps in sequence, captures all output to a log, and records whether the job succeeded or failed. Each execution of a job is called a **build**, and every build is assigned an incrementing numeric ID (Build #1, Build #2, etc.), which makes it fully traceable over time.

---

### Types of Jenkins Jobs: Freestyle vs Pipeline

Jenkins offers several job types. The two most important are **Freestyle** and **Pipeline**.

A **Freestyle project** is a graphical, form-based job. You click through a UI, fill in fields, select options from dropdowns, and Jenkins assembles the logic behind the scenes. It is excellent for beginners and simple tasks because it requires no scripting knowledge. However, it has a serious limitation: the configuration lives inside Jenkins itself (not in your code repository), which makes it hard to version-control, review, or reproduce.

A **Pipeline job**, on the other hand, is defined using a script (written in Groovy-based DSL), usually stored in a file called `Jenkinsfile` inside the code repository. This is the professional, industry-standard approach. It is version-controlled alongside the application code, which means every change to the CI/CD process is tracked, reviewable, and rollback-able just like application code changes. In this lecture, Freestyle is used purely for conceptual understanding, and the course will shift to Pipelines for all real work.

The key insight: Freestyle makes the invisible visible. By seeing all the sections laid out graphically — Source Code Management, Triggers, Build Steps, Post-build Actions — you immediately understand the *anatomy* of a CI/CD pipeline before writing a single line of code.

---

### The Anatomy of a Jenkins Job: Sections Explained

Every Jenkins job is structured around four major sections, each serving a distinct and logical purpose.

**1. Description** — This is a plain-text label for the job. In professional environments, a good description is essential because teams often manage hundreds of jobs. Without descriptions, understanding what a job does requires reading its full configuration. This is a minor but real operational habit.

**2. Source Code Management (SCM)** — This tells Jenkins *where to fetch the source code* before running any build steps. Jenkins supports Git, SVN, and others. You provide a repository URL and credentials, and Jenkins automatically clones or pulls the latest code into the workspace before executing your build logic. This section is what connects Jenkins to GitHub, GitLab, Bitbucket, etc. It is covered in the next lecture.

**3. Build Triggers** — This section defines *when* the job runs. Options include: run manually (clicking "Build Now"), run on a schedule (like a cron job, e.g., every night at midnight), run when a new commit is pushed to the repository (webhook-based), or run after another job completes (chaining jobs). Triggers are what make automation fully autonomous — a developer pushes code, and Jenkins automatically picks it up and runs the pipeline without any human intervention.

**4. Build Steps** — This is where the actual work happens. Build steps are the ordered list of tasks Jenkins will execute. Each step can be a shell command, a Maven build, a NodeJS script, an Ant task, etc. The available step types depend on which **plugins** are installed. This is the heart of every Jenkins job.

**5. Post-build Actions** — These are tasks that run *after* all build steps complete, regardless of whether the build succeeded or failed (unless configured otherwise). Common post-build actions include: sending email notifications, archiving build artifacts, publishing test reports, triggering downstream jobs, or deploying to a server. They represent the "what happens next" phase of automation.

---

### Jenkins Plugins: The Extension System

Jenkins ships as a minimal core. Almost all functionality — Git integration, Maven support, NodeJS, email notifications, Kubernetes deployment, Slack notifications — comes from **plugins**. Plugins are independently developed and installable modules that extend Jenkins's capabilities.

The connection to jobs is direct: the options you see in "Add build step" depend entirely on which plugins are installed. If you install the NodeJS plugin, a "Execute NodeJS script" option appears. If you install the Maven plugin, you get a Maven build step. This modular design is why Jenkins is so widely adopted — it can integrate with virtually any tool in the DevOps ecosystem by installing the right plugin.

A common mistake beginners make is expecting features to "just be there" without understanding the plugin model. When you don't see an expected option in the UI, the answer is almost always: the relevant plugin isn't installed.

---

### The Jenkins Workspace: Where Work Happens

Every Jenkins job has a **workspace** — a dedicated directory on the filesystem of the machine (or agent) running Jenkins. This is where all job-related files live during and after execution. Files created by build steps (compiled binaries, test reports, log files, generated artifacts) are placed here.

The path follows a predictable pattern: `/var/lib/jenkins/workspace/<JobName>/`. For a job named "FirstJob", the workspace is at `/var/lib/jenkins/workspace/FirstJob/`.

The workspace is **temporary by nature**. Jenkins can wipe it clean ("Wipe Out Current Workspace") at any time, and this is often done intentionally to ensure clean builds — you don't want leftover files from a previous build contaminating the next one. This is a critical DevOps principle called **build reproducibility**: every build should produce the same output regardless of what previous builds left behind.

Here's where a subtle but important concept emerges: the workspace and **artifacts** are different things. The workspace is a runtime working directory — ephemeral. Artifacts are files explicitly preserved by post-build actions — persistent. If you need a file to survive beyond the workspace lifecycle, you must archive it.

---

### Build Artifacts: Preserving Important Outputs

An **artifact** in Jenkins is any file produced during a build that you want to keep and make accessible. This could be a compiled `.jar` file, a test report, a packaged Docker image layer, or in this lecture's example, a `.txt` file.

Post-build actions allow you to define artifact archiving rules using glob patterns. The pattern `**/*.txt` means: *recursively search all directories and archive every file with a `.txt` extension.* The `**` is a recursive wildcard (matches zero or more directories), `/` is a path separator, and `*.txt` matches any filename ending in `.txt`.

Archived artifacts are stored permanently within Jenkins (linked to that specific build), accessible from the job's main page under "Last Successful Artifacts". This is essential in real systems because you often need to inspect *exactly what was produced* by a specific build — for auditing, debugging, or deployment purposes.

---

### The Jenkins User and Linux Privilege Model

This is one of the most practically important concepts in this lecture. Jenkins runs as a **dedicated system user** called `jenkins` (on Linux systems). This user is created during Jenkins installation and is intentionally given minimal privileges for security reasons.

When a Jenkins job runs shell commands, those commands execute with the permissions of the `jenkins` user — not `root`, not your personal user account. This has real consequences:

- Commands that require elevated privileges (like `sudo apt update`) will fail because the `jenkins` user does not have sudo access by default.
- Files created during builds are owned by the `jenkins` user and `jenkins` group.
- Network operations, file system access, and system modifications are all bounded by what the `jenkins` user is allowed to do.

This is by design — it is a **security boundary**. If Jenkins had root access and someone injected malicious commands into a build script, those commands would run as root and could destroy or compromise the entire server. By running as an unprivileged user, the damage a compromised job can do is limited.

The real-world implication: when you need Jenkins to do something that requires elevated access (install system packages, modify system files), the professional solution is NOT to give Jenkins root access. Instead, you pre-install dependencies on the Jenkins agent, use Docker containers with pre-built images, or use configuration management tools like Ansible that handle privilege escalation safely.

---

### Job Failure Propagation: How Jenkins Determines Success/Failure

Jenkins determines a build's success or failure based on **exit codes**. Every command executed in a shell returns an exit code: `0` means success, any non-zero value means failure. If any build step returns a non-zero exit code, Jenkins immediately marks that build step as failed and, by default, marks the entire job as failed — it stops executing subsequent steps.

This behavior is called **fail-fast**, and it's intentional. In CI/CD, you want to know as soon as possible that something is broken. You don't want to continue deploying software when a critical step (like compilation or testing) has already failed.

However, there are scenarios where you *want* a step to fail without failing the entire job — for example, a linting step that produces warnings. Jenkins Pipelines (not Freestyle) provide mechanisms to handle this: you can wrap steps in `try-catch` blocks or use the `catchError` directive to control failure propagation precisely. This is one of the reasons Pipelines are more powerful than Freestyle jobs.

## ⚙️ SECTION 2: PRACTICAL (GUIDED EXECUTION MODE)

---

### What We Are Building and Why It Matters

In this practical session, we are creating our **very first Jenkins job** — a Freestyle project that executes Linux shell commands, generates a file, archives it as a build artifact, and demonstrates the full lifecycle of a Jenkins build. We will also deliberately trigger a failure to understand how Jenkins handles errors.

This matters in the real world because every complex CI/CD pipeline — no matter how sophisticated — is built on exactly these primitives: execute commands, handle failures, produce and archive outputs. Understanding these fundamentals gives you the mental model to debug any pipeline, regardless of how complex it becomes.

The final outcome is a working Jenkins job that runs successfully, produces a `cpuinfo.txt` file in its workspace, archives it as a persistent artifact, and teaches you the complete anatomy of a Jenkins build lifecycle.

---

### Step 1: Creating a New Jenkins Job

Navigate to your Jenkins dashboard. You will see two ways to create a job: a "Create a job" link in the center of the screen (visible when no jobs exist yet) and a **"New Item"** link in the left-hand navigation panel. Both do the same thing. Click **New Item**.

You are now on the job creation screen. Jenkins asks you to provide two things: a **name** and a **job type**.

For the name, type `FirstJob`. Job names in Jenkins are important — they become part of the workspace path and the URL. Avoid spaces and special characters in production; use underscores or camelCase. Jenkins allows spaces but they create ugly encoded URLs (`%20`).

For the job type, select **Freestyle project**. You will see other options like Pipeline, Multi-branch Pipeline, etc. — ignore these for now. Click **OK**.

You are now inside the job configuration screen. This is the graphical interface for defining everything about how this job behaves.

---

### Step 2: Understanding and Filling the Configuration Sections

In the **Description** field, type something meaningful like `"We are learning Jenkins job"`. This is a simple operational habit — always describe what a job does so your teammates (and future you) don't have to reverse-engineer it.

Scroll through the page and observe the sections: General, Source Code Management, Build Triggers, Build Environment, Build Steps, Post-build Actions. Do not configure Source Code Management or Build Triggers yet — leave them at their defaults (None / no triggers). These are covered in subsequent lectures.

---

### Step 3: Adding the First Build Step — Shell Commands

Scroll down to the **Build Steps** section. Click **"Add build step"** and select **"Execute shell"** from the dropdown.

A text area appears where you can type shell commands. Enter the following commands, each on a new line:

```bash
whoami
pwd
w
id
```

Here is what each command does and why it matters:

**`whoami`** — Prints the name of the user currently executing the command. In Jenkins's case, this will output `jenkins`, confirming that all build steps run under the `jenkins` system user, not root or your personal account.

**`pwd`** — Stands for "Print Working Directory." It outputs the full filesystem path of the directory where the commands are being executed. This will reveal the workspace path, something like `/var/lib/jenkins/workspace/FirstJob`. This confirms that Jenkins creates a dedicated directory for each job.

**`w`** — A Linux command that shows who is currently logged into the system, how long the system has been running, and the current load average (how busy the CPU is). In a Jenkins context, it shows you the system-level context in which the job is running.

**`id`** — Prints the real and effective user ID (UID), group ID (GID), and supplementary group memberships of the current user. This gives you detailed privilege information about the `jenkins` user — more precise than `whoami`.

Click **Save** at the bottom of the page.

---

### Step 4: Running the Job and Reading the Console Output

You are now on the FirstJob page. Click **"Build Now"** in the left panel. You can click it multiple times to create multiple builds. Jenkins queues them and executes them sequentially.

After a few seconds, you will see the **Build History** panel (bottom-left) populate with build entries: `#1`, `#2`, `#3`, etc. Each entry has a colored indicator: **blue/green** means success, **red** means failure.

Click on the **colored icon** (not the build number — the icon) next to any successful build. This takes you directly to the **Console Output** — a real-time or historical log of everything that happened during that build execution.

Read the console output carefully from top to bottom:

- **"Started by user Admin"** — Jenkins records *who* triggered the build. "Admin" is the username of the logged-in Jenkins user who clicked "Build Now."
- **"Running as SYSTEM"** — This refers to Jenkins's internal execution context.
- **"Building in workspace /var/lib/jenkins/workspace/FirstJob"** — Confirms where on the filesystem the job is running.
- **`+ whoami`** followed by `jenkins` — The `+` prefix means "this is a command being executed." The next line is the output. You can see the job is running as the `jenkins` user.
- **`+ pwd`** followed by `/var/lib/jenkins/workspace/FirstJob` — Confirms the workspace path.
- **`+ w`** — Shows load average and session information.
- **`+ id`** — Shows `uid=XXX(jenkins) gid=XXX(jenkins) groups=XXX(jenkins)` — confirming the exact privilege level.
- **"Finished: SUCCESS"** — All commands exited with code 0, so the build succeeded.

This console output is your primary debugging tool in Jenkins. Every time a build fails, you come here first to find out exactly which command failed and why.

---

### Step 5: Deliberately Triggering a Failure — Understanding Error Propagation

Go back to the job page and click **"Configure"** in the left panel. Scroll down to the Build Steps section and click **"Add build step" → "Execute shell"**. This adds a *second* build step after the first one. Enter:

```bash
sudo apt update
```

**`sudo`** — "Superuser Do." Runs the following command with root (administrator) privileges.
**`apt`** — The Advanced Package Tool, used on Debian/Ubuntu-based Linux to manage software packages.
**`update`** — Tells `apt` to refresh the list of available packages from the internet.

This command requires root access. The `jenkins` user does not have sudo privileges by default, so this will fail.

Click **Save**, then **Build Now**. Watch the Build History — the new build will appear with a **red X** (failure indicator).

Click on the failure icon to open Console Output. You will see that the first build step (`whoami`, `pwd`, `w`, `id`) ran successfully. Then the second build step ran `sudo apt update` and produced an error like `sudo: a terminal is required to read the password` or `jenkins is not in the sudoers file`. Jenkins received a non-zero exit code from this command, immediately declared the build step as failed, and marked the **entire job** as failed.

Key learning: **one failed step fails the entire job.** This is the default behavior. The job does not attempt any subsequent steps after a failure. This ensures broken builds are caught immediately and not silently ignored.

---

### Step 6: Generating a File in the Workspace — Real Artifact Production

Go back to Configure. **Remove** the `sudo apt update` step entirely (there is a delete/remove button next to each build step). In the first build step, replace the existing commands with:

```bash
cat /proc/cpuinfo > cpuinfo.txt
ls -ltr
pwd
```

**`cat /proc/cpuinfo`** — `cat` reads and outputs the contents of a file. `/proc/cpuinfo` is a special virtual file in Linux (part of the `/proc` virtual filesystem) that contains detailed information about the CPU: model name, number of cores, clock speed, cache size, flags, etc. This file doesn't physically exist on disk — Linux generates it dynamically every time you read it.

**`>`** — This is the **output redirection operator**. Instead of printing the output to the screen (console), it writes it into a file. If the file doesn't exist, it creates it. If it does exist, it overwrites it.

**`cpuinfo.txt`** — The name of the file to create. Since no path is specified, it is created in the current directory — which is the Jenkins workspace: `/var/lib/jenkins/workspace/FirstJob/cpuinfo.txt`.

**`ls -ltr`** — Lists directory contents in long format (`-l`), including hidden files, sorted by modification time (`-t`) in reverse order (`-r`, oldest first). This command serves as a verification step — it shows you all files in the workspace, confirming that `cpuinfo.txt` was created.

**`pwd`** — Confirms the current working directory one more time for absolute clarity.

Click **Save**, then **Build Now**.

Open Console Output. You will see `cat /proc/cpuinfo` redirect the CPU data silently (no screen output because of the `>` redirect). Then `ls -ltr` will show `cpuinfo.txt` listed in the workspace, owned by `jenkins:jenkins`. Then `pwd` confirms the path. The build ends with "Finished: SUCCESS."

---

### Step 7: Accessing the Workspace and Viewing the File

Go back to the FirstJob main page (click "FirstJob" in the breadcrumb). In the left panel, you will see a **"Workspace"** link. Click it. You will see the workspace contents listed: `cpuinfo.txt` is there. Click the filename to view its contents directly in the browser — it will show all the CPU information that was captured. You can also click **"Download All Files as Zip"** to download the entire workspace contents.

This is the workspace — the live, current state of the job's working directory. It is useful for quickly inspecting what a build produced without SSH-ing into the server.

Now, click **"Wipe Out Current Workspace"** (also in the Workspace view). Jenkins deletes all files in the workspace. Click the Workspace link again — it is empty. This demonstrates the ephemeral nature of the workspace. If you run Build Now again, the workspace is regenerated from scratch.

---

### Step 8: Archiving Artifacts with Post-build Actions

The workspace being ephemeral is a problem if you need to retain build outputs long-term. This is solved by **archiving artifacts**. Go back to Configure. Scroll all the way to the bottom to the **Post-build Actions** section. Click **"Add post-build action"** and select **"Archive the artifacts"**.

In the **"Files to archive"** field, enter:

```
**/*.txt
```

Breaking this pattern down:

- **`**`** — Double star (globstar). Matches zero or more directories recursively. It means "look everywhere, including inside subdirectories."
- **`/`** — Path separator between the recursive wildcard and the filename pattern.
- **`*.txt`** — Single star followed by `.txt`. Matches any filename that ends with `.txt`. The `*` here matches any sequence of characters in a filename (but not directory separators).

Combined: *Recursively find any `.txt` file anywhere in the workspace and archive it.*

Click **Save**, then **Build Now**. After the build completes successfully, go to the FirstJob main page. You will see a new section: **"Last Successful Artifacts"** with `cpuinfo.txt` listed and available for download. Now wipe out the workspace again. Notice: the workspace is empty, but **"Last Successful Artifacts"** still shows `cpuinfo.txt`. The artifact has been preserved independently of the workspace lifecycle.

This is the distinction that matters: workspace files are temporary runtime files; archived artifacts are permanently preserved build outputs tied to a specific build ID, accessible forever (or until Jenkins is configured to clean old builds).

### Connecting It All: The Full Job Lifecycle

The complete mental model for a Jenkins Freestyle job lifecycle is:

1. **Trigger fires** (manual click, schedule, or webhook from code commit)
2. **Jenkins allocates a workspace** (creates or reuses the directory)
3. **SCM step runs** (clones/pulls code from Git — not configured here, but happens in real jobs)
4. **Build steps execute in order** (each step's exit code is checked; non-zero = fail-fast)
5. **Post-build actions run** (archive artifacts, send emails, notify Slack, etc.)
6. **Build result is recorded** (SUCCESS or FAILURE, stored with full console log)
7. **Workspace may or may not be cleaned** (depending on configuration)

Every real-world Jenkins pipeline — no matter how complex — is this same lifecycle, just with more sophisticated build steps and richer post-build actions. Mastering this mental model means you can reason about any Jenkins job you encounter, whether it's a simple Freestyle project or a 500-line declarative Pipeline.
