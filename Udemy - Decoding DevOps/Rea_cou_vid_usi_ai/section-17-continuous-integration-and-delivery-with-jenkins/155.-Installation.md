# Deep Learning Material: Jenkins Installation on AWS EC2

---

## 🧠 SECTION 1: THEORY (DEEP LEARNING MODE)

---

### CI/CD — The Foundation Concept

Before anything else, you need to understand what problem CI/CD solves. In traditional software development, developers would write code independently for days or weeks, then try to merge everything together at the end. This is called "integration hell" — the longer you wait to integrate, the more conflicts, bugs, and failures pile up. The solution is to integrate code continuously, test it automatically, and deploy it reliably. This is the entire philosophy behind CI/CD.

**CI — Continuous Integration** means that every time a developer pushes code to the shared repository, an automated system immediately picks that code up, builds it (compiles it if needed), and runs all the tests. If anything breaks, the team knows within minutes rather than weeks. The goal is to always keep the codebase in a working, tested state.

**CD — Continuous Delivery or Continuous Deployment** extends this further. After code passes tests, the same automated system can package it, push it to staging or production environments, and release it to end users. The entire pipeline — from a developer typing code to users receiving the feature — becomes automated, fast, and reliable.

In real DevOps environments, this matters enormously. Without CI/CD, a team of 20 developers might deploy once a month, with each deployment being a stressful, risky event. With CI/CD, the same team can deploy dozens of times a day, confidently, because every change is small, tested, and automated.

The keywords that signal CI/CD are: **code, build, test, deploy, release, automated build and release cycle.** Any time you hear these in combination, someone is describing a CI/CD pipeline.

---

### Jenkins — What It Is and Why It Exists

Jenkins is a CI/CD automation server. It is the engine that orchestrates all the steps in your pipeline. Think of it as a highly intelligent task scheduler that knows: "when code is pushed, run these commands in this order, notify these people if something fails."

Jenkins is described as a **legacy CI/CD tool**, and this word "legacy" needs careful explanation. It does not mean Jenkins is obsolete or bad. It means Jenkins has been around since 2011 (originally as "Hudson"), has an enormous ecosystem, and is deeply embedded in thousands of enterprise systems worldwide. It is called legacy because newer, more opinionated tools have since emerged.

Jenkins is **built on Java**. This is architecturally significant for several reasons. First, it means Jenkins itself requires the Java runtime to execute. Second, it means Jenkins can run on any platform where Java runs — Linux, Windows, macOS. Third, since Jenkins is Java-based and you will also be building Java applications on Jenkins, you need the **Java Development Kit (JDK)**, not just the Java Runtime Environment (JRE). This distinction is critical and explained in detail below.

The most powerful characteristic of Jenkins is its **plugin architecture**. Jenkins at its core is a relatively simple job-scheduling engine. Almost every real capability — integrating with Git, sending email notifications, building Maven projects, connecting to AWS, triggering Slack messages — comes through plugins. Plugins are the features of Jenkins. This design makes Jenkins infinitely extensible and customizable, which is why it has survived and thrived for over a decade despite heavy competition.

---

### JRE vs JDK — A Critical Distinction

This is one of the most commonly misunderstood concepts for beginners, and it directly affects whether Jenkins can build your application.

**JRE (Java Runtime Environment)** is the minimum software you need to **run** a Java program. It contains the Java Virtual Machine (JVM), standard class libraries, and other components. If someone hands you a compiled `.jar` file and says "run this," the JRE is all you need.

**JDK (Java Development Kit)** contains everything in the JRE, plus the tools needed to **develop and build** Java programs. This includes the Java compiler (`javac`), debugging tools, and build utilities. If you need to take Java source code and compile it into a runnable program, you need the JDK.

In the context of Jenkins: Jenkins itself only needs the JRE to run. But when Jenkins is going to **build a Java application** (like the vProfile application referenced in the lecture), it needs to compile that Java source code. For that, you need the JDK. This is why the installation command uses `openjdk-21-jdk` and not `openjdk-21-jre`. Using JRE would allow Jenkins to start but fail the moment it tries to compile any Java code.

**OpenJDK** is the open-source, free implementation of the Java Platform. It is the standard choice for servers and CI/CD systems. Version 21 is a Long-Term Support (LTS) release, meaning it receives security updates for many years — making it a safe choice for production and lab environments.

---

### Jenkins Plugins — The Feature System

Understanding Jenkins plugins is essential because you will interact with the plugin system constantly. A plugin in Jenkins is a packaged extension that adds a specific capability. The plugin system is what allows Jenkins to be a general-purpose automation platform rather than a tool locked into one workflow.

When you first install Jenkins, you are shown a screen asking whether to install "suggested plugins" or to manually select. The suggested plugins are a curated set that covers the most common needs: Git integration, build pipeline visualization, email notifications, credential management, and more.

Individual plugins correspond to individual features. The **NodeJS plugin** allows Jenkins to manage Node.js installations and run Node.js-based build steps. The **Git plugin** allows Jenkins to clone repositories. The **Email Extension plugin** allows Jenkins to send detailed email notifications. Each plugin, once installed, adds configuration options in the Jenkins settings and adds steps you can use in your jobs.

Common mistake: people think Jenkins has all features built in and plugins are just "extras." In reality, even basic things like Git support, most build tools, and notification systems require plugins. The core Jenkins without plugins is quite bare.

---

### Jenkins Jobs — The Unit of Work

A Jenkins **job** (also called a "pipeline" in modern Jenkins) is the core unit of work. It is a configured set of steps that Jenkins will execute. Think of it like a shell script, but with a visual interface, logging, scheduling, and trigger capabilities built in.

A job can be configured to: pull code from a Git repository, run a Maven or Gradle build, execute unit tests, build a Docker image, deploy to a server, send notifications, and much more. All of these steps happen in sequence, and if any step fails, Jenkins records the failure, marks the job as failed, and can notify the team.

In a real DevOps pipeline, a job might look like this: developer pushes to GitHub → Jenkins detects the push via webhook → Jenkins pulls the code, runs `mvn clean package`, runs unit tests, builds a Docker image, pushes to ECR, deploys to ECS. All of this is automated and tracked.

### Jenkins Security Architecture — Initial Password and Users

Jenkins uses a layered security model. When first installed, Jenkins generates a long random string and writes it to a specific file on the server. This is the **initial admin password** stored at `/var/lib/jenkins/secrets/initialAdminPassword`. This design exists to prevent unauthorized access during the setup window — if someone could just visit your server's port 8080 immediately after installation without any password, it would be a serious security risk.

Once you unlock Jenkins with that initial password, you create a permanent admin account with a username and password of your choosing. This admin account has full control over Jenkins — creating jobs, installing plugins, managing users, configuring the system.

The **`/var/lib/jenkins/` directory** is the Jenkins home. Everything Jenkins knows — its configuration, job definitions, build history, plugin data, credentials — lives in this directory. This is critically important for operations: if you want to back up Jenkins, you back up this directory. If you want to migrate Jenkins to a new server, you install Jenkins fresh on the new server, copy this directory over, and Jenkins picks up exactly where it left off.

---

### Jenkins Port — Why 8080?

Jenkins runs its web interface on port **8080** by default. This is the same port Apache Tomcat uses by default, which is not a coincidence — both are Java-based web applications and 8080 is a conventional alternative to port 80 (HTTP) that doesn't require root privileges to bind on Linux.

In production environments, it's common to put Jenkins behind a reverse proxy (Nginx or Apache) that listens on port 80 or 443 (HTTPS) and forwards traffic to Jenkins on 8080. For lab purposes, accessing `http://<server-ip>:8080` directly is standard practice.

---

### AWS Security Groups — The Firewall Layer

A **Security Group** in AWS is a virtual firewall that controls inbound and outbound traffic to an EC2 instance. It works on an allow-only model: by default, all inbound traffic is denied, and you explicitly allow what you need.

For Jenkins, you need two inbound rules:
- **Port 22 (SSH)** — to connect to the server via terminal
- **Port 8080 (TCP)** — to access the Jenkins web UI from a browser

The source for both can be set to **"My IP"** which restricts access to only your current public IP address. This is a security best practice for lab environments — you don't want your Jenkins server accessible to the entire internet.

The important warning here: if you have a dynamic IP address (which most home internet connections have), your public IP changes periodically. If you can no longer SSH or access Jenkins from the browser, the first thing to check is whether your IP has changed and whether the security group rule needs updating.

---

### EC2 User Data — Automated Bootstrapping

**User Data** is a feature of AWS EC2 that allows you to provide a shell script that runs automatically when an instance first boots. This is the standard way to automate server provisioning — instead of launching an instance and manually SSHing in to install software, you provide the script upfront and the instance configures itself.

The script must begin with `#!/bin/bash` — this is called a **shebang line**. It tells the Linux kernel which interpreter should execute the file. Without this line, the system doesn't know the file is a bash script and will not execute it correctly.

User Data runs once, at first boot, as the root user. This means you don't need `sudo` inside user data scripts. It also means if the script fails halfway through, you need to SSH in and run the remaining commands manually — user data does not retry failed commands automatically.

The `-y` flag in apt commands (`apt install -y`) tells the package manager to automatically answer "yes" to any prompts. Without it, the installation would pause and wait for user confirmation — but since user data runs non-interactively with no human at the terminal, it would hang forever.

---

### The Known Jenkins URL Bug

There is a well-known issue in Jenkins where setting the Jenkins URL to a public EC2 IP causes performance problems — Jenkins becomes very slow. The root cause is that Jenkins uses this URL internally for various operations, and when the IP is incorrect or unreachable from the server itself, operations time out. The workaround is to set a fake, non-resolving URL (like `jenkins.hkh.xyz`) or to use the EC2's private IP instead of public IP. This is a practical, real-world consideration that many Jenkins tutorials omit.

## ⚙️ SECTION 2: PRACTICAL (GUIDED EXECUTION MODE)

---

### What We Are Building and Why

We are setting up a **Jenkins CI/CD server on an AWS EC2 instance running Ubuntu 24**. This server will act as the automation backbone for our DevOps pipeline. Once running, Jenkins will be capable of pulling code from a Git repository, building a Java application, running tests, and eventually deploying to other servers.

The final outcome is a Jenkins web UI accessible at `http://<ec2-public-ip>:8080`, with an admin account configured, essential plugins installed, and the Jenkins service running persistently in the background as a Linux system service.

---

### Step 1 — Prepare the Installation Commands

Before touching AWS, you need to prepare all the commands you'll use in EC2 User Data. Go to the official Jenkins documentation at `jenkins.io`, navigate to **Documentation → Installing Jenkins → Linux → Debian/Ubuntu**. This ensures you are using the most current, officially supported installation method.

You will find two groups of commands:

**Group 1 — Install Java (OpenJDK 21):**
```bash
sudo apt-get install -y openjdk-21-jdk
```

The original documentation command installs `openjdk-21-jre`. You must change `jre` to `jdk`. Here's why every part matters:
- `sudo` — run with superuser privileges (not needed in user data since it runs as root, but harmless to include)
- `apt-get install` — use the APT package manager to install a package
- `-y` — automatically confirm all prompts without waiting for human input
- `openjdk-21-jdk` — install OpenJDK version 21, specifically the full Development Kit (not just the Runtime)

**Group 2 — Install Jenkins (4 commands in sequence):**

```bash
sudo wget -O /usr/share/keyrings/jenkins-keyring.asc \
  https://pkg.jenkins.io/debian-stable/jenkins.io-2023.key
```
This downloads the GPG signing key for the Jenkins package repository and saves it to `/usr/share/keyrings/`. APT uses this key to verify that downloaded packages are genuinely from Jenkins and haven't been tampered with. This is a security mechanism — without it, you could be installing a malicious package.

```bash
echo "deb [signed-by=/usr/share/keyrings/jenkins-keyring.asc]" \
  https://pkg.jenkins.io/debian-stable binary/ | sudo tee \
  /etc/apt/sources.list.d/jenkins.list > /dev/null
```
This adds the Jenkins repository to your system's list of package sources. By default, Ubuntu's package manager only knows about Ubuntu's official repositories. Jenkins is not in those repos, so you must tell APT where to find it. The `signed-by` parameter links this repository to the key you just downloaded, ensuring every package from this repo is verified.

```bash
sudo apt-get update
```
This refreshes APT's package index — it reads all configured repositories (including the newly added Jenkins one) and updates the local database of available packages. If you skip this step, APT won't know Jenkins exists even though you added the repository.

```bash
sudo apt-get install jenkins -y
```
Now APT can find Jenkins in its updated index, download it, and install it. The `-y` flag is critical here for non-interactive execution.

---

### Step 2 — Assemble the Full User Data Script

Open any text editor. Assemble the complete script that will go into EC2 User Data:

```bash
#!/bin/bash
sudo apt-get install -y openjdk-21-jdk
sudo wget -O /usr/share/keyrings/jenkins-keyring.asc \
  https://pkg.jenkins.io/debian-stable/jenkins.io-2023.key
echo "deb [signed-by=/usr/share/keyrings/jenkins-keyring.asc]" \
  https://pkg.jenkins.io/debian-stable binary/ | sudo tee \
  /etc/apt/sources.list.d/jenkins.list > /dev/null
sudo apt-get update
sudo apt-get install jenkins -y
```

The `#!/bin/bash` line at the very top is mandatory. Without it, EC2 will not know this is an executable bash script and will not run it. This is the single most common reason user data scripts silently fail.

---

### Step 3 — Launch the EC2 Instance

Log into the **AWS Management Console** and navigate to **EC2**. Click **Launch Instance**.

**Name:** `Jenkins-Server` — giving it a meaningful name helps when you have multiple instances running.

**AMI:** Select **Ubuntu Server 24.04 LTS** — this is the operating system that will run on the instance. LTS means Long-Term Support, receiving security updates for 5 years, making it appropriate for a server that will run for an extended period.

**Instance Type:** Select **t2.medium** — this provides 2 vCPUs and 4GB RAM. Jenkins is a Java application and Java applications are memory-hungry. Running Jenkins on the free-tier t2.micro (1GB RAM) will cause it to run extremely slowly or crash during builds. t2.medium is the minimum practical choice for Jenkins. **Important:** t2.medium is not free tier — stop or terminate this instance when not in use to avoid unexpected AWS charges.

**Key Pair:** Click **Create new key pair**, give it the name `cicd-key`. This creates a `.pem` file that downloads to your machine. This file is your SSH private key — it proves your identity when connecting to the server. Keep it safe; it cannot be recovered if lost. The same key will be reused for other servers in this project.

---

### Step 4 — Configure the Security Group

In the **Network Settings** section, click **Edit**. In the **Security Group Name** field, type `jenkins-sg`. Also add the same name to the description. Naming the security group is not optional best practice here — it is functionally important because later in the course you will need to find and modify this security group by name. An unnamed or poorly named security group becomes nearly impossible to identify among many.

Add the following inbound rules:

**Rule 1 — SSH:**
- Type: SSH
- Port: 22
- Source: My IP
- Purpose: Allows you to connect to the server via terminal

**Rule 2 — Jenkins Web UI:**
- Type: Custom TCP
- Port: 8080
- Source: My IP
- Purpose: Allows your browser to access the Jenkins web interface

Setting source to "My IP" rather than "Anywhere" is a security measure. It restricts access to only your current public IP. If you later cannot access Jenkins, check whether your IP has changed (this happens with most home ISPs) and update this rule.

---

### Step 5 — Add User Data and Launch

Scroll down to **Advanced Details**. Scroll to the very bottom of the expanded section until you see the **User Data** text box.

Paste your complete script here, beginning with `#!/bin/bash`. Double-check that:
- The shebang line is the very first line
- Both `-y` flags are present (on the JDK install and Jenkins install lines)
- There are no typos in the repository URL

Click **Launch Instance**. AWS will provision the server, boot Ubuntu, and automatically execute your script. The entire process takes approximately 5 minutes.

---

### Step 6 — Verify Installation via SSH

After 5 minutes, find your instance in the EC2 console and copy its **Public IPv4 address**.

Open your terminal (Git Bash on Windows, Terminal on Mac/Linux) and run:

```bash
ssh -i ~/Downloads/cicd-key.pem ubuntu@<your-ec2-public-ip>
```

Breaking this command down completely:
- `ssh` — the Secure Shell client program that creates an encrypted connection to a remote server
- `-i ~/Downloads/cicd-key.pem` — the `-i` flag specifies the **identity file** (your private key). The path `~/Downloads/cicd-key.pem` assumes you downloaded the key to your Downloads folder — adjust if needed
- `ubuntu` — the username on the remote server. Ubuntu AMIs always use `ubuntu` as the default user, not `root` or `ec2-user`
- `@<your-ec2-public-ip>` — the address of the server you're connecting to

Once connected, switch to root:
```bash
sudo -i
```

Verify Java is installed:
```bash
java -version
```

**Expected output:**
```
openjdk version "21.0.x" ...
```

If you see an error like "command not found," your user data script did not execute correctly. You must run the installation commands manually, one by one, in this SSH session.

Verify Jenkins is running:
```bash
systemctl status jenkins
```

**Expected output:** You will see `Active: active (running)` highlighted in green. Press `q` to exit this view.

If Jenkins is not running, start it manually:
```bash
systemctl start jenkins
```

---

### Step 7 — Understand the Jenkins Directory Structure

While SSH'd in, examine the Jenkins home directory:
```bash
ls -la /var/lib/jenkins/
```

This directory is the **heart of your Jenkins installation**. Everything important lives here: job configurations, build history, plugin files, credentials, the secrets directory containing the initial password, and the global configuration file.

The directory is owned by the `jenkins` user and `jenkins` group. This Linux user was automatically created during Jenkins installation. Jenkins runs as this user — meaning all Jenkins processes, all file operations, and all build executions happen under the `jenkins` user account. This is a security best practice: Jenkins should not run as root.

**Migration knowledge:** If you ever need to move Jenkins to a new server, the process is: stop Jenkins (`systemctl stop jenkins`), archive this entire directory (`tar -czf jenkins-backup.tar.gz /var/lib/jenkins/`), install Jenkins fresh on the new server, stop Jenkins on the new server, replace its `/var/lib/jenkins/` with your archive, fix ownership (`chown -R jenkins:jenkins /var/lib/jenkins/`), and restart Jenkins. Your entire Jenkins history, jobs, and configuration will be intact.

### Step 8 — Access Jenkins in the Browser

In your browser, navigate to:
```
http://<your-ec2-public-ip>:8080
```

You will see the **"Unlock Jenkins"** page. Jenkins requires you to prove you have server access by providing the initial password that was written to the server's filesystem.

Back in your SSH terminal, retrieve it:
```bash
cat /var/lib/jenkins/secrets/initialAdminPassword
```

`cat` reads and prints the content of a file to the terminal. The output will be a long alphanumeric string — copy it entirely, paste it into the Jenkins browser field, and click **Continue**.

---

### Step 9 — Select and Install Plugins

You are presented with two choices:
- **Install suggested plugins** — installs a predefined useful set automatically
- **Select plugins to install** — shows you the list and lets you customize

Choose **Select plugins to install**. This approach is recommended because it teaches you what's being installed and gives you control.

On the plugin selection screen, browse through the categories. Notice:
- Under **Build Tools**: uncheck **Ant** (you won't need it), check **NodeJS** (you will need it for Node.js-based projects)
- **Git** is already selected — this is essential for pulling source code
- **Email Extension** is in the Notifications section — this enables build failure notifications

Once you've reviewed and adjusted selections, click **Install**. Jenkins will download and install each selected plugin. This may take 2-5 minutes depending on network speed. You will see a progress screen showing each plugin being installed.

---

### Step 10 — Create the Admin User

After plugins install, you reach the admin user creation form. Fill in:
- **Username:** `admin`
- **Password:** something you will remember (for labs, even a simple password works, but note it down)
- **Full Name:** `admin`
- **Email:** any email (can be fake for labs, e.g., `admin@ops.com`)

Click **Save and Continue**. This creates a permanent admin account. Jenkins will use this account going forward — the initial password file is no longer needed after this point.

---

### Step 11 — Handle the Jenkins URL (Bug Workaround)

The next screen asks you to confirm the **Jenkins URL**. It will be pre-filled with `http://<your-ec2-public-ip>:8080/`.

Do NOT keep this value. This public IP will change every time you stop and restart your EC2 instance. More importantly, keeping a changing IP here causes a known Jenkins bug where the server becomes extremely slow because internal Jenkins operations that reference this URL start timing out.

**The fix:** Replace the URL with any fake, non-resolving hostname:
```
http://jenkins.hkh.xyz/
```

This doesn't need to be a real domain. Jenkins just needs a value here that won't cause it to make outbound network calls to a changing IP. Click **Save and Finish**.

You will see **"Jenkins is ready!"** — click **Start using Jenkins** and you are on the Jenkins dashboard.

---

### Step 12 — Explore the Jenkins Dashboard

The main page shows options to **create a job**. The left sidebar shows **Manage Jenkins** (the gear icon) — this is where all global settings live.

Click **Manage Jenkins** and explore:
- **System** — global configuration including the Jenkins URL you just set. You can fix the URL here if needed later.
- **Tools** — configure which versions of JDK, Git, Maven, NodeJS etc. Jenkins should use for builds
- **Plugins** — install, update, remove, enable, or disable plugins
- **Credentials** — store sensitive data (SSH keys, passwords, API tokens) that Jenkins jobs can use securely

Click **System** and scroll down — you will see your configured Jenkins URL. This confirms the URL setting was saved. The home directory shown (`/var/lib/jenkins`) confirms Jenkins is using the correct data directory.

To return to the dashboard at any time, click the **Jenkins logo** in the top-left corner.

You can also explore the **Appearance** settings in your user account (top-right corner) to switch between light and dark themes — dark mode is available and fully functional.

---

### Connecting It All Together

What you have built is a fully operational Jenkins server that is: secured behind AWS security group rules, running as a persistent system service (it will auto-start if the EC2 instance reboots), accessible via browser, equipped with essential plugins, and configured with an admin account. The Jenkins home directory at `/var/lib/jenkins` is the single source of truth for this entire installation.

From here, every subsequent step in the CI/CD journey — creating pipelines, integrating with GitHub, building Java applications, deploying to servers — happens through jobs configured on this Jenkins instance. The plugin system means you can extend it to support virtually any tool or workflow your pipeline requires.
