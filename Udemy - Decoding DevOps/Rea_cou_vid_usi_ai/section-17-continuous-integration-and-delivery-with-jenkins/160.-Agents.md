# Jenkins Agents — Deep Learning Material

---

## 🧠 OUTPUT SECTION 1: THEORY (DEEP LEARNING MODE)

---

### Concept 1: The Problem with a Single Machine Running Everything

To understand Jenkins agents, you first need to understand why they exist. Imagine you have a single Jenkins server. Every job you create — building a Java application, running tests, compiling a .NET project, packaging a Docker image — all of it runs on that one machine. This creates several serious problems in real-world systems.

First, **resource exhaustion**. A build job for a large Java project using Maven can consume significant CPU and RAM. If five developers push code simultaneously and Jenkins tries to run five Maven builds at once on one machine, that machine can run out of memory, slow to a crawl, or crash entirely. The Jenkins server itself (which manages the UI, job scheduling, plugin execution, and configuration) is now competing for the same CPU and RAM as the build jobs. This is dangerous because if the server goes down mid-build, you lose everything.

Second, **operating system limitation**. A .NET application using MSBuild or a Windows-specific framework cannot be compiled on a Linux machine. Similarly, iOS applications require a macOS environment. If your Jenkins server runs on Linux, you simply cannot build Windows or Mac projects on it natively. You need different machines with different operating systems.

Third, **tool version conflicts**. One project might need JDK 11, another needs JDK 17, and yet another needs JDK 21. Managing all these versions on a single machine and switching between them cleanly for different jobs is fragile and error-prone. It leads to "works on my machine" problems at the CI/CD level.

Jenkins agents solve all three problems in one architectural decision.

---

### Concept 2: What is a Jenkins Agent (Distributed Architecture)?

A Jenkins agent — also historically called a "node" or "slave" (the latter term is now deprecated and should not be used) — is a **separate computer** that connects to the Jenkins master (also called the Jenkins controller) and executes build jobs on its behalf.

The architecture looks like this: there is one central Jenkins master, and connected to it are one or more agent machines. The master is the brain — it handles the UI, stores job configurations, schedules builds, manages plugins, and decides which agent should run which job. The agents are the workers — they receive instructions from the master and execute them, then return results.

This is called **distributed architecture** because the work of building software is distributed across multiple machines rather than concentrated on one. The word "distributed" here doesn't mean geographically spread (though it can be), it means functionally separated — each machine has a dedicated role.

The master never needs to know *how* to build the project. It only needs to know *which agent* is capable of building it and *what commands* to send. The agent receives those commands and executes them in its own environment, using its own installed tools, its own operating system, and its own resources.

---

### Concept 3: How Master-Agent Communication Works Internally

The Jenkins master communicates with agents using several protocols. The most common in real-world use are **SSH** (for Linux/Mac agents) and **JNLP/TCP** (for Windows agents or when SSH is not available).

When SSH is used (as in this lecture), here is exactly what happens internally:

The Jenkins master initiates an SSH connection to the agent machine using a private key credential stored securely inside Jenkins. This is standard public-key SSH authentication — the agent machine has a public key authorized for login, and Jenkins holds the corresponding private key. Once the SSH connection is established, Jenkins uploads a small Java program called the **agent JAR** (also called `remoting.jar`) to the agent machine, placing it inside the configured remote root directory (e.g., `/opt/jenkins`). This JAR acts as the communication bridge — it runs on the agent and keeps a persistent connection open with the master.

From this point, whenever a job is assigned to this agent, the master sends the build instructions (shell commands, Maven goals, Git clone commands, etc.) through this channel to the agent JAR, which executes them on the local agent machine. The output (logs, console output) is streamed back to the master in real time, which is why you see live logs in the Jenkins UI even though the build is running on a different machine.

This is why **JDK must be installed on the agent** — the agent JAR is a Java program. It cannot run without a Java runtime. Maven, on the other hand, does not need to be pre-installed because Jenkins can download and manage Maven itself through the Tools configuration and place it on the agent.

---

### Concept 4: Labels — The Routing System for Jobs

Labels are one of the most important concepts in Jenkins distributed architecture. A **label** is a tag or identifier that you assign to an agent. When configuring a job, you can specify a label expression, and Jenkins will only run that job on agents that match that label.

Think of labels like job descriptions in a company. You label one agent as "MAVENBUILDER" — meaning this machine has everything needed to build Maven projects. You label another agent as "DOTNET-BUILDER." Now, when a Java/Maven project needs to be built, the job references the "MAVENBUILDER" label, and Jenkins automatically routes it to the correct agent.

Labels also enable **job isolation**. By setting the agent's usage policy to "Only build jobs with label expressions matching this node," you ensure the agent is never accidentally used for unrelated jobs. The default setting ("Use this node as much as possible") means Jenkins will send any available job to it, which can undermine the purpose of specialization.

In real DevOps pipelines, you might have labels like: `linux`, `windows`, `docker`, `gpu`, `maven`, `nodejs`, `arm64`. A pipeline job can even use multiple agents with different labels in different stages — for example, compile on `linux-maven`, test on `linux-maven`, and deploy on `windows-iis`.

---

### Concept 5: Executors — Parallelism within a Single Agent

The **number of executors** on an agent defines how many jobs can run *simultaneously* on that agent. If you set executors to 2, Jenkins can send two jobs to that agent at the same time, and they will run in parallel. A third job will wait in the queue until one of the two slots becomes free.

This is a resource management decision. You need to think about how much RAM and CPU the agent has, and how much each build job consumes. If a Maven build consumes 1GB of RAM and your agent has 4GB, setting executors to 4 is risky — four simultaneous Maven builds could exhaust memory and cause all four to fail. Setting executors to 2 is safer, even if it means some jobs wait.

In production, organizations often use **auto-scaling agents** — cloud-based agents (on AWS EC2, GCP, or Kubernetes pods) that are spun up on demand when a job arrives and terminated after the job completes. This makes the executor count less critical because each agent only runs one job and then disappears. But for static, persistent agents (as configured in this lecture), executor count is a deliberate tuning decision.

---

### Concept 6: The Remote Root Directory

The **remote root directory** is a path on the agent machine where Jenkins will store everything it needs: the agent JAR file, tool installations (like Maven, downloaded automatically), and the workspace for each job (where code is cloned and built).

In this lecture, `/opt/jenkins` is used. This is a conventional choice — `/opt` is a standard Linux directory for optional or add-on software, and placing Jenkins-related files there keeps things organized. However, the directory must exist and must be writable by the SSH user Jenkins uses to connect (in this case, the `ubuntu` user).

This is why the ownership change command (`chown ubuntu:ubuntu /opt/jenkins`) is critical. If the `ubuntu` user doesn't have write permission to this directory, Jenkins will fail to upload the agent JAR and the connection will fail — even if SSH authentication succeeds. This is a very common error when setting up agents for the first time.

---

### Concept 7: Host Key Verification and Why It's Disabled Here

When you SSH into a Linux machine for the first time, SSH shows you the server's fingerprint and asks: "Are you sure you want to connect? Type yes or no." This is a security mechanism to prevent man-in-the-middle attacks — you're confirming that the machine you're connecting to is the one you intended.

In an automated system like Jenkins, there's no human to type "yes." The SSH connection happens in the background, programmatically. If Jenkins encounters this prompt and can't respond, the connection hangs and eventually times out.

The solution used here is **"Non-verifying Verification Strategy"** — Jenkins skips the host key check entirely. This is acceptable in a controlled internal environment (like AWS VPC, where the agent is a machine you just created and fully control), but it does introduce a minor security trade-off: if the agent IP were somehow hijacked, Jenkins wouldn't detect it.

In high-security production environments, you would use **"Manually provided key"** or **"Known hosts file"** strategies, where you pre-register the agent's fingerprint so Jenkins can verify it without human interaction. But for learning environments and internal builds, non-verifying is the pragmatic and widely-used choice.

---

### Concept 8: Why Maven is NOT Pre-installed on the Agent

This is a subtle but important concept. JDK must be manually installed on the agent because the agent JAR itself is a Java program — without Java, nothing runs. But Maven does not need to be pre-installed.

Jenkins has a **Tool Auto-Installer** feature. When you configure a Maven tool in Jenkins (e.g., "Maven 3.9") and assign it to a job, Jenkins will automatically download that exact version of Maven from the internet the first time the job runs on an agent that doesn't have it yet, unpack it into the agent's remote root directory, and set the `PATH` and `MAVEN_HOME` environment variables for that job. Subsequent builds reuse the already-downloaded Maven.

This is powerful because it means agents don't need to be manually configured with specific tool versions. The job itself declares what it needs, and Jenkins handles provisioning it. This also means you can have different jobs using Maven 3.6, 3.8, and 3.9 on the same agent without conflicts — each version is stored separately.

## ⚙️ OUTPUT SECTION 2: PRACTICAL (GUIDED EXECUTION MODE)

---

### What We Are Building

We are connecting a separate Ubuntu EC2 instance (the "Maven agent") to a Jenkins master (controller) so that Jenkins can delegate build jobs to it via SSH. The agent will be labeled "MAVENBUILDER" and we will configure existing Jenkins jobs to run on this agent instead of the master. This simulates a real-world distributed CI/CD setup where build workloads are offloaded from the Jenkins server to dedicated build machines.

The final outcome: when you trigger a build job in Jenkins, the console output will say **"Building remotely on MAVENBUILDER"** — meaning the job ran on the agent, not the master.

---

### Step 1: Launch the Agent EC2 Instance

We start by creating a new Ubuntu EC2 instance that will serve as our Jenkins agent. Go to the AWS EC2 console and click **Launch Instance**.

**Name it:** `Maven agent` — this is just a human-readable label in AWS so you can identify it easily.

**Operating System:** Select Ubuntu (Ubuntu 24.04 LTS is fine). We use Ubuntu because it's a widely-used Linux distribution in DevOps, familiar tooling, and compatible with all commands we'll run.

**Instance type:** Choose `t2.small` instead of `t3.micro`. The reason is that build jobs — especially Maven builds that compile Java code, download dependencies, and run tests — can be memory-intensive. A `t2.small` has slightly more RAM than a `t3.micro` and will handle Maven builds more reliably without running out of memory mid-build.

**Key pair:** Use the same key pair you've been using for this course (e.g., the CI/CD `.pem` file). This is important — you need the private key file locally to SSH into the agent and also to paste its contents into Jenkins later.

---

### Step 2: Configure the Security Group for the Agent

This is a critical networking step. The security group acts as a firewall for the EC2 instance. We need two SSH rules:

**Rule 1 — SSH from your IP:**
- Type: SSH
- Port: 22
- Source: My IP

This allows you (the engineer) to SSH into the agent from your laptop to install software and configure it manually.

**Rule 2 — SSH from Jenkins Security Group:**
- Type: SSH
- Port: 22
- Source: Select "Custom" and choose your Jenkins master's security group (e.g., `jenkins-sg`)

This allows the Jenkins master EC2 instance to initiate an SSH connection to this agent. Jenkins will use this SSH connection to upload the agent JAR and send build instructions. Without this rule, Jenkins can never connect to the agent — it will time out during the connection attempt.

Give this security group a descriptive name like `mavenagent-sg` and an equally clear description. Click **Launch Instance**.

---

### Step 3: SSH into the Agent and Install JDK

Once the instance is running, copy its **public IP** address from the AWS console. Open your terminal and SSH into it:

```bash
ssh -i /path/to/your-key.pem ubuntu@<AGENT_PUBLIC_IP>
```

Breaking this down:
- `ssh` — the SSH client command
- `-i /path/to/your-key.pem` — specifies the identity file (your private key). The `-i` flag means "identity"
- `ubuntu` — the default username for Ubuntu EC2 instances (AWS creates this user automatically)
- `@<AGENT_PUBLIC_IP>` — the address of the machine to connect to

Once logged in, switch to the root user so subsequent commands don't require `sudo` for every line:

```bash
sudo -i
```

Now install OpenJDK 21:

```bash
apt update && apt install openjdk-21-jdk -y
```

Breaking this down:
- `apt update` — refreshes the package index so `apt` knows about the latest available package versions. Without this, you might install an outdated version or get a "package not found" error
- `&&` — runs the next command only if the previous one succeeded
- `apt install openjdk-21-jdk` — installs OpenJDK 21 (the full JDK, not just the JRE, because the agent JAR needs full Java development kit capabilities)
- `-y` — automatically answers "yes" to any confirmation prompts, making it non-interactive

After installation completes, verify it worked:

```bash
java -version
```

You should see output like `openjdk version "21.x.x"`. If you see this, JDK is correctly installed.

**Why JDK and not just JRE?** The agent JAR (`remoting.jar`) that Jenkins uploads is a Java application. Running Java applications requires at minimum a JRE (Java Runtime Environment), but installing the full JDK is safer and is standard practice for build agents since build tools often need JDK-specific tools (like `javac`).

---

### Step 4: Create the Jenkins Working Directory and Set Permissions

Jenkins needs a dedicated directory on the agent to store its files — the agent JAR, tool installations (like Maven), and job workspaces. Create it:

```bash
mkdir -p /opt/jenkins
```

- `mkdir` — make directory
- `-p` — create parent directories if they don't exist (safe to use even if the directory already exists)
- `/opt/jenkins` — the path we've chosen. `/opt` is the conventional Linux location for optional software

Now set ownership so the `ubuntu` user (which Jenkins will use for SSH) can read and write to this directory:

```bash
chown ubuntu:ubuntu /opt/jenkins
```

- `chown` — change ownership
- `ubuntu:ubuntu` — sets both the **user owner** and the **group owner** to `ubuntu`
- `/opt/jenkins` — the directory to change ownership on

Verify the permissions:

```bash
ls -ld /opt/jenkins
```

- `ls` — list
- `-l` — long format (shows permissions, owner, group, size, date)
- `-d` — show the directory itself, not its contents

Expected output looks like:
```
drwxr-xr-x 2 ubuntu ubuntu 4096 Jan 1 00:00 /opt/jenkins
```

The `ubuntu` user has `rwx` (read, write, execute) — this means Jenkins can write files here, which is essential. Without write permission, Jenkins will fail to upload the agent JAR.

Now log out of the agent:

```bash
exit
```

---

### Step 5: Copy the Private Key Content for Jenkins

Jenkins needs the private key to authenticate its SSH connection to the agent. From your **local machine** (not the agent), print the content of your `.pem` file:

```bash
cat /path/to/your-key.pem
```

The output will look like:

```
-----BEGIN RSA PRIVATE KEY-----
MIIEowIBAAKCAQEA...
(many lines of base64 characters)
...
-----END RSA PRIVATE KEY-----
```

Select and copy **everything** from `-----BEGIN RSA PRIVATE KEY-----` through `-----END RSA PRIVATE KEY-----`, inclusive. Do not miss the first or last line. Do not include any trailing spaces or blank lines. Any corruption of this key content will cause Jenkins to fail with an authentication error.

Keep this copied to your clipboard — you'll paste it into Jenkins momentarily.

---

### Step 6: Add the Agent in Jenkins — Create the Node

Go to your Jenkins UI. Navigate to: **Manage Jenkins → Nodes → New Node**.

- **Node name:** `MavenBuilder` — this is the internal Jenkins identifier for this agent
- **Type:** Select **Permanent Agent** — this means the agent is always available (as opposed to ephemeral cloud agents that are created and destroyed per job)
- Click **Create**

You'll now see the node configuration form. Fill it in as follows:

**Number of Executors:** Set to `1`. This means only one job can run on this agent at a time. We set it to 1 because we're working in a learning environment with a small instance. In production, you'd tune this based on available RAM and CPU.

**Remote Root Directory:** `/opt/jenkins` — this is exactly the directory we created on the agent. Jenkins will place the agent JAR here and create job workspaces as subdirectories of this path.

**Labels:** `MAVENBUILDER` (all caps) — this is the label that jobs will reference to select this agent. The exact casing matters — if the job uses `MAVENBUILDER` and you type `mavenbuilder` here, they won't match.

**Usage:** Select **"Only build jobs with label expressions matching this node"** — this prevents Jenkins from randomly sending unrelated jobs to this agent. The agent will only be used when a job explicitly requests the `MAVENBUILDER` label.

**Launch Method:** Select **"Launch agents via SSH"** — Jenkins will initiate the SSH connection.

**Host:** Enter the **private IP** of the agent EC2 instance (not the public IP). Why private IP? Because the Jenkins master and the Maven agent are both in the same AWS VPC (Virtual Private Cloud). Communication within a VPC using private IPs is faster, free (no data transfer charges), and doesn't require the agent to have a public IP at all. You can find the private IP in the AWS EC2 console on the agent's details page.

---

### Step 7: Add SSH Credentials in Jenkins

Next to the **Credentials** field, click **Add → Jenkins**. A credential dialog opens. Configure it:

- **Kind:** SSH Username with private key — this tells Jenkins the credential type, which determines how it will authenticate
- **ID:** `maven-agent-login` — a unique identifier for this credential within Jenkins. You'll reference this if you ever need to programmatically retrieve it
- **Description:** `maven agent login` — human-readable description
- **Username:** `ubuntu` — this is the Linux user on the agent that Jenkins will SSH as. For Ubuntu EC2 instances, this is always `ubuntu` (set by AWS automatically)
- **Private Key:** Select **"Enter directly"**, then click **Add** and paste the full content of your `.pem` file that you copied in Step 5

Click **Add** to save the credential. Back in the node configuration, select this new credential from the **Credentials** dropdown.

---

### Step 8: Configure Host Key Verification

In the **Host Key Verification Strategy** field, select **"Non verifying Verification Strategy"**.

As explained in the theory section, when SSH connects to a new machine for the first time, it asks the user to verify the host fingerprint. Since Jenkins is automating this connection, there's no human to type "yes." This setting tells Jenkins to skip that verification step entirely. In a controlled AWS environment where you created the agent yourself, this is safe and is the standard approach for new Jenkins setups.

Click **Save**.

---

### Step 9: Verify the Agent Connected Successfully

After saving, you're taken to the Nodes list. Click on **MavenBuilder** to open the agent page. Click on **Log** in the left sidebar.

Read through the log output. You're looking for the line:

```
Agent successfully connected and online
```

If you see this, the agent is connected and ready to receive jobs. Jenkins has successfully SSHed into the agent, uploaded the agent JAR to `/opt/jenkins`, and established a persistent communication channel.

**If you see errors instead**, here is a systematic troubleshooting checklist:

1. **Authentication failure** — The private key was copied incorrectly. Return to Step 5, re-copy the key carefully, and update the credential in Jenkins
2. **Connection timed out / Connection refused** — The security group rule allowing SSH from Jenkins to the agent is missing or wrong. Return to Step 2 and verify Rule 2 uses the correct Jenkins security group
3. **Permission denied on /opt/jenkins** — The `chown` command in Step 4 wasn't run, or was run incorrectly. SSH back into the agent and re-run it
4. **Java not found** — JDK installation failed or the wrong package was installed. SSH back and verify with `java -version`

---

### Step 10: Configure a Jenkins Job to Use the Agent

Now we'll tell an existing job to run on this agent. Go to any existing job in Jenkins (e.g., your Maven build job for `vprofile`), click **Configure**.

In the **General** section, find the checkbox: **"Restrict where this project can be run"**. Check it. A **Label Expression** field appears. Type `MAVENBUILDER`.

Jenkins will validate the label — if the label exists and matches a connected agent, you'll see a confirmation message like "Label MAVENBUILDER matches 1 node." If it doesn't match anything, you'll see a warning, which means either the agent isn't connected or the label text doesn't exactly match.

Also, ensure the **Maven version** is set to "Maven 3.9" (or whatever version you configured under Manage Jenkins → Tools). This ensures Jenkins downloads and installs Maven 3.9 on the agent automatically during the first build.

Click **Save**, then click **Build Now**.

---

### Step 11: Verify the Build Ran on the Agent

Click on the build number to open it, then click **Console Output** (or "Click to see full log"). Look for this at the top:

```
Building remotely on MAVENBUILDER (MAVENBUILDER) in workspace /opt/jenkins/workspace/<job-name>
```

This confirms the job ran on the agent. Further down in the log, you'll see:

```
Unpacking https://...apache-maven-3.9...zip to /opt/jenkins/tools/...
```

This is Jenkins downloading Maven 3.9 onto the agent automatically. And if the job includes a `whoami` command, you'll see it outputs `ubuntu` — confirming the build is running as the `ubuntu` user on the agent machine, via SSH.

---

### Step 12: Cleanup — Remove Agent Label and Terminate Instance

When your experiments are done, you must clean up in the correct order:

**First, remove the label from all jobs.** Go to each job's Configure page, uncheck "Restrict where this project can be run," and save. If you terminate the agent while jobs still reference its label, those jobs will sit in the queue indefinitely waiting for an agent with that label — they'll never run and will show a "waiting for next available executor" message.

**Second, delete the agent from Jenkins.** Go to **Manage Jenkins → Nodes**, click on **MavenBuilder**, and select **Delete Agent**. Confirm the deletion. This removes the agent configuration from Jenkins cleanly.

**Third, terminate the EC2 instance.** Go to the AWS EC2 console, select the Maven agent instance, click **Instance State → Terminate**. This stops billing for the instance.

The correct cleanup order is: jobs → Jenkins agent → EC2 instance. Doing it in reverse order (terminating EC2 first) is not catastrophic, but Jenkins will show the agent as offline and repeatedly try to reconnect, generating error logs until you delete it from the Nodes list.

### The Complete Mental Model

When you trigger a build job configured with `MAVENBUILDER`:

1. Jenkins master receives the build trigger
2. Master checks which connected agents match the label `MAVENBUILDER`
3. Master initiates SSH connection to the agent using the stored private key credential
4. Master uploads/reuses the agent JAR at `/opt/jenkins/remoting.jar`
5. Agent JAR starts and opens a communication channel back to the master
6. Master sends build instructions through this channel (git clone, mvn package, etc.)
7. Agent executes each instruction in its local environment, using its JDK and the auto-installed Maven
8. Console output streams back to the master in real time
9. Build artifacts (JAR files, test reports) are stored in `/opt/jenkins/workspace/<job-name>/` on the agent
10. Master records the build result (success/failure) and stores logs

This is the foundation of every scaled CI/CD system in the industry — whether using static EC2 agents like this, Docker-based agents, or Kubernetes pod-based agents, the core master-agent-label-executor model remains the same.
