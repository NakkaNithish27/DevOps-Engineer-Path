### 1. What is a Jenkins Build Job?

A Jenkins Build Job is the fundamental unit of work in Jenkins. Think of it as a defined recipe that Jenkins follows every time you want to build, test, or package your software. It is not just a script — it is a structured, configurable entity that knows *where* to fetch code, *what tools* to use, *what steps to execute*, and *what to do after* those steps finish.

In the real world, every software project needs to be compiled, tested, and packaged repeatedly — every time a developer pushes new code. Without automation, a developer would manually run commands, check results, and distribute output files. This is error-prone, slow, and impossible to scale across a team of dozens of developers. A Jenkins build job eliminates that manual process by encoding all those steps once, and then executing them reliably on demand or automatically on code changes.

Internally, when a Jenkins job runs, it creates a **workspace** — a dedicated directory on the Jenkins server's filesystem — clones the source code into it, executes the configured build steps using the specified tools, and then performs post-build actions like archiving artifacts. Each run is called a **build**, and Jenkins maintains a history of all builds with their logs and outcomes.

In real DevOps systems, build jobs are the first stage of a CI/CD pipeline. They are the gatekeepers: no artifact gets deployed unless the build job succeeded. A failed build job is a signal to the team that the code is broken, and it prevents broken code from ever reaching production.

### 2. Freestyle Project vs. Other Job Types

Jenkins offers several job types: Freestyle Project, Pipeline, Multibranch Pipeline, and others. The **Freestyle Project** is the oldest and most visual job type. You configure everything through a graphical UI — dropdowns, text fields, checkboxes. It is the best starting point for learning Jenkins because it exposes every configuration option visually, making the underlying concepts obvious.

In contrast, a **Pipeline job** uses a `Jenkinsfile` — a script written in Groovy — to define the same steps programmatically. Pipelines are more powerful, more portable, and better for production systems, but they require understanding the Freestyle concepts first. You cannot understand what `stage('Build') { sh 'mvn install' }` means in a pipeline if you do not first understand why Maven is needed and what "install" does.

The Freestyle Project is not inferior — it is appropriate for simple, single-branch builds and for learning. Real-world systems often use both: Freestyle for auxiliary tasks and Pipelines for main CI/CD flows.

### 3. Tools in Jenkins: The Plugin–Binary Relationship

This is one of the most misunderstood concepts for Jenkins beginners, and the instructor specifically emphasizes it repeatedly for good reason.

Every tool Jenkins uses has **two layers**:

**Layer 1 — The Plugin (Frontend):** A Jenkins plugin adds *awareness* of a tool to the Jenkins UI. For example, the Git plugin adds a "Source Code Management" section in the job configuration with a Git option. The Maven plugin adds the "Invoke top-level Maven targets" build step. Without the plugin, Jenkins does not know the tool exists and you cannot configure it graphically.

**Layer 2 — The Actual Binary (Backend):** The plugin alone does nothing if the actual tool binary is not available on the system. The Git plugin needs the `git` command-line tool installed on the Jenkins server. The Maven plugin needs either a Maven installation downloaded automatically or an `mvn` binary already present in the system's PATH.

The failure mode when this is misunderstood is very common: someone installs a plugin but forgets to install or configure the actual tool, and the build fails with cryptic errors like "command not found" or "No such file or directory."

Jenkins provides two ways to make tool binaries available:

**Auto-installation:** In Jenkins → Manage Jenkins → Tools, you configure a tool (e.g., Maven 3.9.14) and check "Install automatically." Jenkins downloads the binary from the internet the first time that tool is needed, stores it under `/var/lib/jenkins/tools/`, and reuses it in subsequent builds. This is clean, version-controlled, and reproducible.

**System-installed binary:** You install the tool on the OS directly (e.g., `apt install maven`) and it lands in the system PATH. Jenkins can then use it as the "default" installation. This approach is less controlled — you don't know which version gets installed until you check, and updating the OS package may silently change the tool version.

In real DevOps environments, **auto-installation is preferred** for reproducibility. If the Jenkins server is rebuilt, auto-installed tools are re-downloaded automatically. System-installed tools need manual reinstallation.

### 4. JDK Versioning and Why It Matters for Build Jobs

Java projects have strict JDK version requirements. A project written for Java 11 APIs may fail to compile or run on JDK 17 because of deprecations or removals. A project using Java 17 features will fail to compile on JDK 11 because those features simply do not exist there.

Jenkins allows you to configure multiple JDK versions (JDK 11, JDK 17, JDK 21) in Tools, and then each job selects which JDK to use. This is powerful because different projects on the same Jenkins server can use different JDK versions without conflict.

Under the hood, when a job runs with a specific JDK configured, Jenkins sets the `JAVA_HOME` environment variable to point to that JDK installation for the duration of that build. Maven, which is itself a Java application and also compiles Java code, reads `JAVA_HOME` to know which Java to use. This is why the JDK selection in a job affects not just the compilation target but also Maven's own runtime.

In real-world systems, you will encounter Java projects that are stuck on older JDK versions because of legacy dependencies. Being able to run those builds on JDK 11 while running newer projects on JDK 21, all on the same Jenkins server, is a critical capability.

### 5. Maven: Goals, the POM, and the Build Lifecycle

Maven is a **build automation tool** for Java projects. It does far more than just compile code — it manages the entire build lifecycle: compiling, running tests, packaging, and installing artifacts.

Maven operates around a concept called **goals**, which are specific tasks it can execute. The most important goal for CI is `install`. When you run `mvn install`, Maven executes a full sequence internally:

1. **validate** — checks the project structure is correct
2. **compile** — compiles the Java source files into `.class` bytecode
3. **test** — runs unit tests using the compiled code
4. **package** — packages the compiled code into a JAR or WAR file
5. **verify** — runs integration checks
6. **install** — copies the packaged artifact into the local Maven repository (`~/.m2/repository`)

This is called the **build lifecycle**. Each goal triggers all preceding goals automatically. So `mvn install` does not just install — it compiles, tests, packages, and then installs. This is why a single `mvn install` command is sufficient to produce a fully built, tested artifact.

The **POM (Project Object Model)** file — `pom.xml` — is the heart of a Maven project. It declares the project's dependencies, the Java version target, the packaging type (JAR, WAR), plugins, and other configuration. Maven reads this file to know what to do. When Jenkins runs `mvn install`, Maven looks for `pom.xml` in the job's workspace — the same directory where the source code was cloned.

The artifact produced — in this case `vprofilev2.war` — is the deployable output. It is what gets deployed to application servers. Archiving it in Jenkins means Jenkins stores a copy linked to that specific build, so you can always retrieve exactly what was built from build #3 or build #7.

### 6. Credentials Management in Jenkins

When source code lives in a **private** Git repository, Jenkins needs credentials to access it. Jenkins has a built-in **Credentials Store** that securely stores secrets and makes them available to jobs without embedding them in the job configuration in plaintext.

Jenkins supports several credential types:

**Username and Password:** Traditional HTTP-based Git authentication. The username is your Git hosting account username, and the password is typically a Personal Access Token (PAT), not your actual account password, because most Git hosting services (GitHub, GitLab, Bitbucket) have deprecated password-based authentication for API and Git access.

**SSH Username with Private Key:** Git can authenticate over SSH using a key pair. You place the public key in your Git hosting account settings, and store the private key in Jenkins credentials. When Jenkins clones the repository, it uses the private key to authenticate. This is more secure than passwords because keys are long, random, and cannot be guessed.

Each credential gets an **ID** — a human-readable identifier you choose (e.g., `github-ssh-key` or `vprofile-credentials`). This ID is how you reference the credential in job configurations and Jenkinsfiles, without ever exposing the actual secret.

For **public repositories**, credentials are not needed, because anyone can read the code. That is why this lab works without credentials — the repository is public.

### 7. Source Code Management: Branch Specifiers

In a Jenkins job's Source Code Management section, the **branch specifier** tells Jenkins which branch of the repository to check out. By default, it is `*/master` or `*/main`, but you can set it to any branch name.

This is critical in real-world CI because different branches serve different purposes. You may want your CI job to build the `develop` branch for integration testing, but only deploy from the `main` branch. You configure different jobs — or pipeline stages — for each branch.

The branch name `electron` in this lab is just a custom name for a specific version of the vprofile source code. The `JDK11` branch contains code designed to be built with Java 11. If you use the `electron` branch (which targets JDK 17) but configure the job to use JDK 11, you may get compilation failures. This mismatch between branch and JDK version is a common real-world mistake and a deliberate learning exercise here.

### 8. Post-Build Actions and Artifact Archiving

After a build succeeds, Jenkins can perform **post-build actions** — tasks that happen automatically after the main build steps complete. The most important for CI is **artifact archiving**.

When you specify `**/*.war` as the files to archive, Jenkins uses Ant-style path patterns:
- `**` means "search recursively through all subdirectories"
- `*` means "match any filename"
- `.war` means "with this extension"

So `**/*.war` means: find every file ending in `.war`, anywhere in the workspace directory tree, and archive it.

Archiving stores a copy of the artifact inside Jenkins' own storage (`/var/lib/jenkins/jobs/<jobname>/builds/<buildnumber>/archive/`). This serves several purposes: you can download the artifact directly from the Jenkins UI, you can pass it to downstream jobs (like a deployment job), and you have a historical record of what was built for each build number.

In real DevOps pipelines, artifact archiving is the bridge between the Build stage and the Deploy stage. The deploy job picks up the archived artifact and deploys it to the target environment.

---

### 9. Why Plugins Are Preferred Over Shell Commands

The instructor explicitly emphasizes: **always prefer plugins over shell commands**. This deserves deep understanding.

When you use "Execute Shell" and type `mvn install`, Jenkins runs that as a raw shell command. Jenkins has no awareness of what Maven version was used, where it came from, or how to validate it. If Maven is not in the system PATH, it fails silently with a confusing error.

When you use the "Invoke top-level Maven targets" plugin step, Jenkins:
1. Knows exactly which Maven installation to use (because you selected it from the dropdown)
2. Sets all required environment variables before running Maven
3. Provides additional configuration options (POM path, properties, Java options) through the UI
4. Integrates with Jenkins' tool management system

The plugin approach is more **portable** (works across OS types), more **maintainable** (version is explicit), and provides **better error messages** when something goes wrong. Shell commands are a fallback for when no plugin exists for what you need to do.

### What We Are Building

We are creating a Jenkins Freestyle build job that automatically fetches the Java source code of a project called **vprofile** from GitHub, builds it using Maven, and archives the resulting `.war` artifact inside Jenkins. This simulates the most fundamental step of any real CI/CD pipeline: automated, reproducible builds triggered on demand.

The final outcome is a passing Jenkins build that shows a green checkmark, a complete build log you can inspect, and a downloadable `.war` artifact stored in Jenkins — ready to be deployed.

### Step 1: Configure JDK 21 in Jenkins Tools

**What we are doing:** We are registering JDK 21 as a known tool inside Jenkins so that build jobs can select and use it.

**Why we are doing it:** Jenkins needs to know where JDK installations live on the filesystem. By registering them in the Tools section, we make them selectable per-job through a dropdown, enabling different jobs to use different Java versions cleanly.

Navigate to: **Jenkins Dashboard → Manage Jenkins → Tools**

Scroll to the **JDK installations** section. You will already see JDK 17 listed. Click **Add JDK**:

- **Name:** `JDK21` (all caps, as shown — this is the label you will see in job dropdowns)
- **JAVA_HOME:** Copy the path from JDK 17's entry and change `17` to `21` in the path. For example: `/usr/lib/jvm/java-21-openjdk-amd64`
- **Uncheck** "Install automatically" because JDK 21 was already installed on the system during Jenkins installation

This tells Jenkins: "When a job asks for JDK21, use the binary at this exact path." Jenkins will set `JAVA_HOME` to this path before running that job's build steps.

---

### Step 2: Configure Maven 3.9.14 in Jenkins Tools

**What we are doing:** We are adding Maven 3.9.14 as an auto-installed tool in Jenkins.

**Why we are doing it:** The vprofile project requires Maven 3.9+. By configuring it here with a specific version and "Install automatically," Jenkins will download exactly this version the first time a job needs it, guaranteeing reproducibility.

Still in **Manage Jenkins → Tools**, scroll to **Maven installations**. Click **Add Maven**:

- **Name:** `MAVEN3.9.14` (this becomes the label in job dropdowns)
- **Install automatically:** Leave this **checked**
- **Version:** Select `3.9.14` from the dropdown

Click **Save**.

What happens internally when this is first used: Jenkins downloads the Maven 3.9.14 binary archive from Apache's servers and extracts it to `/var/lib/jenkins/tools/hudson.tasks.Maven_MavenInstallation/MAVEN3.9.14/`. On every subsequent build using this tool, Jenkins skips the download and uses the cached installation.

---

### Step 3: Create the Freestyle Job

**What we are doing:** We are creating a new build job and giving it an identity and description.

**Why we are doing it:** Each Jenkins job is an independent unit with its own configuration, history, and workspace. Creating a new job creates a new entry in Jenkins and a new directory in `/var/lib/jenkins/jobs/`.

From the Jenkins dashboard, click **New Item**:

- **Item name:** `vprofile build`
- **Type:** Select **Freestyle project**
- Click **OK**

In the configuration page that opens, add a **Description**: `Vprofile Build - Build job using JDK and Maven`. This is optional but important for real-world jobs so team members understand what a job does without reading its full configuration.

Under **JDK**, use the dropdown to select **JDK17**. This sets the `JAVA_HOME` for this build.

---

### Step 4: Configure Source Code Management (Git)

**What we are doing:** We are telling Jenkins where the source code lives and which branch to use.

**Why we are doing it:** Jenkins needs to fetch the source code before it can build anything. Without source code, there is nothing to compile. The SCM configuration automates the `git clone` that a developer would otherwise run manually.

In the job configuration, scroll to **Source Code Management**. Select **Git** (this option appears because the Git plugin is installed and the `git` binary is present on the system — remember the two-layer concept).

- **Repository URL:** Go to `https://github.com/hkhcoder/vprofile-project`, click the green **Code** button, ensure **HTTPS** is selected, and copy the URL. Paste it into this field.

- **Credentials:** Leave as **None** — this is a public repository, so no authentication is required. For private repositories, you would click **Add → Jenkins**, select the credential type (username/password or SSH key), fill in the details, and then select the saved credential from the dropdown.

- **Branch Specifier:** Change the default (which is usually `*/master`) to `*/electron`. This tells Jenkins to check out the `electron` branch specifically.

Internally, when the job runs, Jenkins executes the equivalent of:
```
git clone -b electron https://github.com/hkhcoder/vprofile-project.git .
```
...inside the job's workspace directory.

---

### Step 5: Add the Maven Build Step

**What we are doing:** We are defining the actual build command — what Jenkins should execute after the source code is fetched.

**Why we are doing it:** Fetching source code does nothing by itself. The build step is where the actual compilation, testing, and packaging happens.

Scroll to **Build Steps**. Click **Add build step** → select **Invoke top-level Maven targets** (do NOT choose "Execute shell" — always prefer the plugin as explained in the theory section).

- **Maven Version:** Select `MAVEN3.9.14` from the dropdown
- **Goals:** Type `install`

The word `install` here is the Maven lifecycle goal. It triggers: validate → compile → test → package → install. The result is a `.war` file in the `target/` subdirectory of the project workspace.

Click **Advanced** to see additional options: you could specify a custom `pom.xml` path (useful if the POM is not in the root), pass Java options, or provide a custom Maven settings file. We leave these at defaults.

---

### Step 6: Add Post-Build Action to Archive Artifacts

**What we are doing:** We are telling Jenkins to save the built `.war` file so it can be accessed after the build completes.

**Why we are doing it:** Build workspaces are temporary — they get overwritten on the next build. Archiving copies the artifact to a permanent location within the Jenkins job's build record, making it downloadable and passable to downstream deployment jobs.

Scroll to **Post-build Actions**. Click **Add post-build action** → select **Archive the artifacts**.

- **Files to archive:** `**/*.war`

Breaking down the pattern:
- `**` — search in the current directory AND all subdirectories recursively
- `/` — path separator
- `*.war` — match any file whose name ends with `.war`

This will find `target/vprofilev2.war` (or whatever the exact artifact name is) anywhere inside the workspace.

Click **Save**.

---

### Step 7: Run the Build and Read the Logs

**What we are doing:** We are triggering the build manually and observing what Jenkins does internally.

**Why we are doing it:** Understanding the logs is how you diagnose failures. Every experienced DevOps engineer reads logs fluently.

Click **Build Now** on the job's main page. A build entry appears in the **Build History** panel on the left. Click the blinking progress bar or the build number to open the build.

Click **Console Output**. Read through it carefully:

1. **Git clone section:** Jenkins logs the clone operation, the repository URL, the branch, and the commit hash it checked out. If this fails, the error is here — wrong URL, wrong branch name, missing credentials.

2. **Maven download section (first run only):** You will see lines like "Unpacking" and a path ending in `/var/lib/jenkins/tools/...`. This confirms Maven is being auto-downloaded. On subsequent runs, this section is replaced by just the tool path being printed.

3. **Maven build output:** Hundreds of lines showing dependency downloads, compilation, test execution, and packaging. Watch for `BUILD SUCCESS` at the end.

4. **Archiving artifacts:** Jenkins logs which files it archived and where.

A successful build ends with `Finished: SUCCESS` and the build ball turns **blue** (or green if you have the Green Balls plugin).

### Step 8: Understanding the Failure — Default Maven

**What we are doing:** We deliberately break the job to understand the difference between plugin-managed tools and system tools.

**Why we are doing it:** You will encounter this failure in real life. Understanding it now means you can diagnose it in under 30 seconds.

Go to **Configure** → Change the Maven version to **Default** (which means "use whatever `mvn` binary the system shell can find in PATH") → **Save** → **Build Now**.

The build will fail. In the console output you will see:
```
mvn install
ERROR: The process '/bin/sh -c mvn install' failed with exit code 127
```
or:
```
/bin/sh: mvn: command not found
```

This happens because when using "Default," Jenkins simply runs `mvn install` as a shell command. If `mvn` is not in the system PATH, the shell cannot find it, and the build fails.

### Step 9: Install Maven System-Wide to Fix the Default Failure

**What we are doing:** We install Maven on the Ubuntu OS so that the `mvn` command exists in the system PATH.

**Why we are doing it:** To demonstrate that the "Default" Maven option works when the system binary exists, and to show what version gets installed via package manager (which you cannot control as precisely as the auto-install method).

SSH into your Jenkins server:
```bash
ssh ubuntu@<JENKINS_PUBLIC_IP>
```

Switch to root:
```bash
sudo -i
```

Install Maven:
```bash
apt update && apt install maven -y
```

Breaking this down:
- `apt update` — refreshes the package index so Ubuntu knows the latest available packages
- `&&` — run the next command only if the previous one succeeded
- `apt install maven` — installs the Maven package from Ubuntu's repositories
- `-y` — automatically answer "yes" to the installation prompt, enabling non-interactive installation

Verify the version:
```bash
mvn -version
```

This will print something like `Apache Maven 3.8.7`. Note this version — it may not match what the project needs. In this case, Maven 3.8.7 happens to work for the vprofile project (though there were previously test failures with 3.8 in earlier versions of the project — always verify).

Now go back to Jenkins and trigger the build again. This time it succeeds because `mvn` exists in the PATH. In the console output, you will notice the difference: the system-installed Maven run shows `mvn install` without a full path prefix, while the plugin-managed run shows the full path `/var/lib/jenkins/tools/.../mvn install`. This distinction in the log tells you immediately which mode Jenkins is using.

### Step 10: The Hands-On Exercise (Understanding by Breaking Things)

**What we are doing:** The instructor assigns a deliberate practice exercise of mismatching JDK versions and branches.

**Why we are doing it:** In real DevOps, builds fail because of mismatches — wrong JDK, wrong Maven version, wrong branch. Experiencing these failures in a safe environment builds the diagnostic instinct you need for production.

The exercise:

1. Install JDK 11 on the Ubuntu machine: `apt install openjdk-11-jdk -y`
2. Register it in Jenkins Tools as `JDK11` with its path (find the path with `update-java-alternatives -l`)
3. Create a new job that uses the `JDK11` branch of the vprofile repo and configures JDK 11
4. Then try using the `electron` branch (which targets JDK 17) with JDK 11 configured — watch it fail
5. Switch back to the `JDK11` branch — watch it succeed

The key insight is this: **branch name and JDK version are not automatically linked**. Jenkins does not know that "electron branch" requires JDK 17. You must configure the correct JDK for each branch manually. This is one reason why real-world projects document their build requirements (often in a `README` or `Jenkinsfile`) so engineers know exactly which JDK and Maven version to use.

This exercise builds the most important DevOps skill: **reading logs to diagnose failures**, understanding what the system is doing internally, and adjusting configuration accordingly rather than guessing.
