# 🧠 SECTION 1: THEORY (Deep Learning Mode)

## 1.1 The Core Problem — Not All Services Have systemctl by Default

On Linux, services are managed through the `systemctl` command — start, stop, restart, enable at boot, check status. When you install a service through the **package manager** (like `dnf` on CentOS), the package manager does more than just copy binaries. It creates configuration files in `/etc/`, log directories in `/var/log/`, library files in `/usr/lib/`, **and** a systemd service file that allows `systemctl` to manage the service. This is why after `dnf install httpd`, you can immediately run `systemctl start httpd` — the package manager created everything, including the systemd file.

But not all software is available through the package manager. Apache Tomcat, for example, is not available via `dnf`. Or you may need a **specific version** that the package manager doesn't offer. In such cases, you download the software manually as a tarball (`.tar.gz`), extract it, and get a folder containing all binaries, configs, and scripts. The problem: **no systemd file gets created**. The system has no idea this software exists as a "service." You can run it manually using its scripts (`startup.sh`, `shutdown.sh`), but `systemctl` cannot see it, manage it, or enable it at boot.

This lecture teaches you how to **bridge that gap** — how to write a custom systemd unit file so that any manually installed software becomes a proper, manageable system service.

## 1.2 Apache httpd vs. Apache Tomcat — A Critical Distinction

The instructor explicitly clarifies: **Apache httpd and Apache Tomcat are two completely different services**, despite both coming from the Apache Software Foundation.

**httpd** is a general-purpose web server — it serves static files (HTML, CSS, images) and can proxy requests to other services. It listens on port 80/443. It is the same Apache2 seen in previous lectures.

**Tomcat** is an **open-source Java servlet container**. It is specifically designed to host **Java-based web applications**. It runs Java code (servlets, JSPs) and serves dynamic content generated by Java. It listens on port **8080** by default. Tomcat requires **Java (JDK/JRE)** as a dependency — without Java installed, Tomcat cannot function.

## 1.3 The Problems with Manual Service Management

When Tomcat is started manually using `bin/startup.sh`, it works — the process runs, the web page loads on port 8080. But two critical problems exist:

**Problem 1 — No boot persistence.** If the machine reboots, Tomcat does not start automatically. Someone must manually SSH in and run `startup.sh` again. In production, this is unacceptable. The `systemctl enable` command (which registers a service to start at boot) only works if a systemd file exists.

**Problem 2 — No standardized management interface for automation.** In DevOps, automation tools like **Ansible** manage services remotely. Ansible's `service` module works by calling `systemctl` under the hood — you just specify the service name and desired state. If there is no systemd file, Ansible cannot manage the service. There is no standard interface. You would have to write custom scripts, which breaks the standardized automation model.

Additionally, stopping a manually-started service requires finding the process ID with `ps -ef | grep tomcat` and then running `kill <PID>`. If the process has spawned child processes (forking), you must kill all of them. This is "doable but complicated." A systemd-managed service handles all of this cleanly with `systemctl stop`.

## 1.4 The systemd Architecture — How Linux Manages Services

`systemctl` is the **command-line interface** to **systemd**, which is the init system and service manager for modern Linux. When you say `systemctl start httpd`, systemctl reads a **unit file** (the systemd configuration file for that service) to know exactly how to start it.

For package-manager-installed services, unit files live at `/usr/lib/systemd/system/`. For custom or user-created service files, the correct location is **`/etc/systemd/system/`**. The file is named `<service-name>.service` — and this file name directly determines the service name used with systemctl. If you name the file `tomcat.service`, the service is managed as `systemctl start tomcat`.

🔍 **Deep Dive — What's Inside a Package-Managed Unit File:**

The instructor demonstrates this by examining httpd's unit file: `cat /usr/lib/systemd/system/httpd.service`. The critical element is the `ExecStart` directive — for httpd, it is `/usr/sbin/httpd $OPTIONS -DFOREGROUND`. This is the **actual command** that systemctl executes when you say `systemctl start httpd`. Every `systemctl start` command ultimately translates to running the command specified in `ExecStart`. The rest of the unit file provides context: dependencies, user identity, environment, stop commands, etc.

## 1.5 The Anatomy of a systemd Unit File — Three Sections

A systemd unit file is structured into three sections (called **directives**), each enclosed in square brackets. Every section has a distinct responsibility:

### \[Unit] — Global Metadata and Dependencies

This section describes **what** the service is and **when** it can start.

**`Description=`** — A human-readable label. Appears in `systemctl status` output and logs. Example: `Description=Tomcat`.

**`After=`** — Declares an **ordering dependency**. `After=network.target` means: "Start this service only after all networking services have started." This is critical for Tomcat because it is a network service — it needs the network stack to be ready before it can bind to port 8080. The `After` directive does not mean "require" — it means "if network.target is being started, start me after it."

The supplementary file also shows `After=syslog.target network.target`, adding syslog as a dependency — ensuring logging is available before Tomcat starts.

### \[Service] — Runtime Configuration

This is the core section — it defines **how** the service runs.

**`User=` / `Group=`** — The Linux user and group under which the service process will execute. For Tomcat, this is `tomcat` — a dedicated non-root user created specifically for this purpose. Services should **never** run as root for security reasons. If the service process is compromised, the attacker only gets the permissions of the `tomcat` user, not root.

**`Type=forking`** — Tells systemd how the service behaves at startup. `forking` means the startup process will fork (create child processes) and the parent will exit. Tomcat's `startup.sh` does exactly this — it launches the Java process as a child and exits. systemd needs to know this so it can correctly track the service's main process.

**`WorkingDirectory=`** — The directory from which the service operates. Set to `/opt/tomcat` (the Tomcat home directory).

**`Environment=`** — Exports environment variables into the service's runtime environment. The instructor makes an important distinction: **these variables are requirements of Tomcat, not of systemd.** systemd is just the mechanism for passing them. The variables:

* `JAVA_HOME=/usr/lib/jvm/jre` — Tells Tomcat where to find the Java runtime. This is where Java gets installed by default on CentOS.
* `CATALINA_HOME=/opt/tomcat` — Tomcat's own home directory variable. Tomcat's internal scripts use this to locate its files.
* `CATALINA_BASE=/opt/tomcat` — Usually the same as CATALINA\_HOME for single-instance setups. Supports multiple Tomcat instances sharing the same binary.

The supplementary file also shows `CATALINA_PID` pointing to a PID file location — used by Tomcat to track its own process ID.

**`ExecStart=` / `ExecStop=`** — The actual commands to start and stop the service. For Tomcat: `ExecStart=/opt/tomcat/bin/startup.sh` and `ExecStop=/opt/tomcat/bin/shutdown.sh`. These are the same scripts you would run manually — systemd just automates their execution.

### \[Install] — Boot Integration

**`WantedBy=multi-user.target`** — This controls what happens when you run `systemctl enable tomcat`. It tells systemd: "When the system reaches multi-user.target during boot, start this service."

The instructor explains the concept of **targets** (runlevels in older terminology): Linux has different operational modes. **multi-user.target** is the standard non-GUI mode where the full operating system is running with all services, but without a graphical desktop. This is the mode a server VM boots into — which is exactly the case for a headless CentOS VM. There is also a GUI target and a "safe mode" equivalent. By specifying `WantedBy=multi-user.target`, you ensure Tomcat starts during normal server boot.

## 1.6 The Service User Pattern — Why Tomcat Needs Its Own User

The `tomcat` user is created with two deliberate restrictions:

1. **`--home-dir /opt/tomcat`** — The user's home directory is set to where Tomcat's files live. This is the conventional way to associate a service user with its data.
2. **`--shell /sbin/nologin`** — The user cannot log in interactively. There is no shell. This is a **security measure** — the user exists solely to own files and run processes. Nobody can SSH in as the `tomcat` user.

All Tomcat files must be **owned by this user** (`chown -R tomcat.tomcat /opt/tomcat`). If the ownership is wrong, the Tomcat process (running as the `tomcat` user) will get "permission denied" errors when trying to read its own binaries or write logs.

## 1.7 daemon-reload — Synchronizing systemd's Knowledge

After creating or modifying any systemd unit file, you **must** run `systemctl daemon-reload`. systemd reads and caches all unit files at boot. If you add a new file or change an existing one, systemd's in-memory state is stale — it doesn't know about your changes. `daemon-reload` forces systemd to re-read all unit files from disk. Without it, `systemctl start tomcat` will either fail (file not recognized) or use the old configuration.

⚠️ **Expert Note:** This is the same pattern seen with Apache's `systemctl reload` — services cache configuration and must be explicitly told to re-read it. The difference: `daemon-reload` reloads **systemd's own** configuration (the unit files), while `systemctl reload <service>` reloads a **service's** configuration (like Apache's `httpd.conf`). These are two different levels of configuration refresh.

## 1.8 The DevOps Perspective — Why This Matters for Automation

The instructor briefly shows an **Ansible** playbook that uses the `service` module. In Ansible, you declare: "service name = tomcat, state = started." Ansible translates this to a `systemctl start tomcat` call on the target machine. If the systemd file doesn't exist, this fails — there is no standard interface for Ansible to interact with.

The broader principle: **systemctl is the universal service management API on modern Linux.** Every automation tool (Ansible, Puppet, Chef, SaltStack), every monitoring system, and every orchestration platform expects services to be manageable through systemctl. Writing a systemd file is not optional in a DevOps environment — it is the **standard contract** that makes a process a proper service.

## 1.9 Reuse Over Memorization — The Instructor's Practical Advice

The instructor explicitly states: "I never write it from scratch." In practice, engineers maintain a library of systemd files — their own, from GitHub repositories, from documentation. You copy an existing systemd file for a similar service and modify it for your needs. The value is in **understanding the structure** so you can adapt any template, not in memorizing the syntax. The systemd file is also provided in the course resource section.

# ⚙️ SECTION 2: PRACTICAL (Guided Execution Mode)

## What We Are Building

We are converting Apache Tomcat from a **manually-started process** into a **systemctl-managed service** on a CentOS VM. The final outcome: `systemctl start tomcat`, `systemctl stop tomcat`, `systemctl enable tomcat`, and `systemctl status tomcat` all work — Tomcat is a proper, boot-persistent, automatable Linux service.

## Step 1: Prepare the CentOS VM

Use an existing CentOS VM from earlier lectures. Bring it up with Vagrant, log in, and switch to root:

```bash
vagrant up
vagrant ssh
sudo -i
```

Verify you are on CentOS:

```bash
cat /etc/os-release
```

## Step 2: Install httpd and Examine Its systemd File (Understanding the Pattern)

Install httpd to observe how a **package-managed** service comes with a ready-made systemd file:

```bash
dnf install httpd -y
```

Check that systemctl works immediately:

```bash
systemctl status httpd
```

Now examine the systemd unit file that the package manager created:

```bash
ls /usr/lib/systemd/system/ | grep httpd
```

```bash
cat /usr/lib/systemd/system/httpd.service
```

**Key observation:** The `ExecStart` line contains the actual binary command that `systemctl start httpd` executes. The three directives — `[Unit]`, `[Service]`, `[Install]` — define the service's metadata, runtime behavior, and boot integration. This is the template pattern we will replicate for Tomcat.

**Connection to flow:** This step is purely educational — we are studying the structure before writing our own.

## Step 3: Download Apache Tomcat Manually

Search "download Tomcat 10" in the browser, go to the Apache Tomcat site, find Binary Distribution → Core → tar.gz, right-click → copy link address.

```bash
wget https://archive.apache.org/dist/tomcat/tomcat-10/v10.1.28/bin/apache-tomcat-10.1.28.tar.gz
```

* `wget` — Command-line download tool.
* The URL points to Tomcat 10.1.28's tarball on Apache's archive.

Extract:

```bash
tar xzvf apache-tomcat-10.1.28.tar.gz
```

* `x` — Extract. `z` — Decompress gzip. `v` — Verbose (show files). `f` — Filename follows.

Verify:

```bash
ls apache-tomcat-10.1.28/
```

You should see: `bin/`, `conf/`, `lib/`, `logs/`, `temp/`, `webapps/`, `work/` — the complete Tomcat package in a single directory.

## Step 4: Install Java (Tomcat's Dependency)

Tomcat is a Java servlet container — it requires a Java runtime to function.

```bash
dnf install java-17-openjdk -y
```

* `java-17-openjdk` — OpenJDK version 17, the open-source Java implementation.

**Verification:**

```bash
java -version
```

Should display `openjdk version "17.x.x"`.

## Step 5: Start Tomcat Manually (To See the Problem)

Navigate into the Tomcat directory and start it:

```bash
cd apache-tomcat-10.1.28/
bin/startup.sh
```

Output should say "Tomcat started."

**Verify the process:**

```bash
ps -ef | grep tomcat
```

You should see a Java process running with Tomcat parameters.

**Verify in browser:** Get the VM's IP (`ip addr show`), enter `http://<IP>:8080` in the browser. The default Tomcat welcome page should appear.

**Now observe the problems:**

* `systemctl status tomcat` → will fail (no systemd file)
* `systemctl enable tomcat` → impossible (no systemd file)
* Stopping requires: `ps -ef | grep tomcat`, then `kill <PID>`

**Stop the process now** (we need a clean state for the systemd setup):

```bash
ps -ef | grep tomcat
kill <PID>
```

Replace `<PID>` with the actual process ID from the `ps` output. The instructor's was `31251`.

**Connection to flow:** This manual start/stop was to demonstrate why systemd is needed. Now we build the proper solution.

## Step 6: Create the Tomcat Service User

```bash
useradd --home-dir /opt/tomcat --shell /sbin/nologin tomcat
```

* `--home-dir /opt/tomcat` — Sets the user's home directory. Also creates this directory.
* `--shell /sbin/nologin` — Prevents interactive login. Security measure (see Theory §1.6).

**Verification:**

```bash
ls -ld /opt/tomcat
```

The directory should exist and be owned by `tomcat`.

## Step 7: Copy Tomcat Files and Set Ownership

```bash
cp -r apache-tomcat-10.1.28/* /opt/tomcat/
```

* `cp -r` — Recursive copy. Copies all contents from the extracted folder to the Tomcat user's home directory.

Set ownership:

```bash
chown -R tomcat.tomcat /opt/tomcat/
```

* `-R` — Recursive. Applies to all files and subdirectories.
* `tomcat.tomcat` — Sets both owner and group to `tomcat`.

**Verification:**

```bash
ls -l /opt/tomcat/
```

All files should show `tomcat tomcat` as owner and group. If ownership is wrong, the service will fail with "permission denied."

**Connection to flow:** The files are now in the right place, owned by the right user. Next, we tell systemd about this service.

## Step 8: Write the systemd Unit File

Create the file at the correct location:

```bash
vim /etc/systemd/system/tomcat.service
```

* `/etc/systemd/system/` — The directory for custom/user-created unit files.
* `tomcat.service` — The filename becomes the service name for systemctl.

Enter insert mode (`i`) and write the following content:

```ini
[Unit]
Description=Tomcat
After=network.target

[Service]
Type=forking

User=tomcat
Group=tomcat

WorkingDirectory=/opt/tomcat

Environment=JAVA_HOME=/usr/lib/jvm/jre
Environment=CATALINA_HOME=/opt/tomcat
Environment=CATALINA_BASE=/opt/tomcat

ExecStart=/opt/tomcat/bin/startup.sh
ExecStop=/opt/tomcat/bin/shutdown.sh

[Install]
WantedBy=multi-user.target
```

**Line-by-line operational reasoning:**

| Line                            | Purpose                                                   |
| ------------------------------- | --------------------------------------------------------- |
| `Description=Tomcat`            | Label shown in `systemctl status`                         |
| `After=network.target`          | Don't start until networking is ready                     |
| `Type=forking`                  | startup.sh forks a child process and exits                |
| `User=tomcat` / `Group=tomcat`  | Run as the dedicated non-root user                        |
| `WorkingDirectory=/opt/tomcat`  | Process runs from this directory                          |
| `Environment=JAVA_HOME=...`     | Tomcat needs this to find Java                            |
| `Environment=CATALINA_HOME=...` | Tomcat's internal home variable                           |
| `Environment=CATALINA_BASE=...` | Tomcat's instance base (same as HOME for single instance) |
| `ExecStart=.../startup.sh`      | Command systemctl executes for `start`                    |
| `ExecStop=.../shutdown.sh`      | Command systemctl executes for `stop`                     |
| `WantedBy=multi-user.target`    | Enable at boot in normal server mode                      |

Save and quit (`:wq`).

⚠️ **Critical:** Be meticulous with spelling and capitalization. A typo in `User=tomcat` (e.g., `Tomcat` vs `tomcat`) will cause a failure because the Linux user is lowercase. A wrong path in `ExecStart` will fail with "file not found."

🔍 **Deep Dive — The supplementary reference file** ([58-tomcat\_service\_file.txt](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/58-tomcat_service_file.txt?EntityRepresentationId=b6b4aa47-ff2d-4e36-9e18-73dde2d3a642)) shows a slightly different version with `CATALINA_PID` pointing to a PID file, and paths at `/usr/local/tomcat/` instead of `/opt/tomcat/`. This demonstrates the template-and-adapt pattern — the structure is identical, only paths and specific variables change per deployment.

## Step 9: Reload systemd, Start, and Enable

```bash
systemctl daemon-reload
```

**Mandatory.** Tells systemd to re-read all unit files from disk. Without this, systemd doesn't know `tomcat.service` exists.

**Pre-check:** Make sure no Tomcat process is already running from the earlier manual start:

```bash
ps -ef | grep tomcat
```

If any exist, `kill <PID>` them. Two Tomcat instances on the same port will conflict.

Start the service:

```bash
systemctl start tomcat
```

If there are errors (typos in the unit file, wrong paths, permission issues), the error message will appear here.

**Verify:**

```bash
systemctl status tomcat
```

Should show **"active (running)"**.

Enable at boot:

```bash
systemctl enable tomcat
```

Now Tomcat will automatically start when the VM reboots.

**Browser verification:** Navigate to `http://<VM-IP>:8080` — the Tomcat welcome page should appear, same as the manual start, but now managed by systemd.

## Troubleshooting

If `systemctl start tomcat` fails:

1. **Check the error message** displayed by `systemctl start`.
2. **Check status details:** `systemctl status tomcat -l` (full log).
3. **Common causes:**
   * Typo in the unit file (path, username, variable name)
   * Wrong ownership on `/opt/tomcat/` (not `tomcat:tomcat`)
   * Java not installed (`JAVA_HOME` points to nothing)
   * A manually-started Tomcat process is already occupying port 8080
   * Missing `daemon-reload` after creating/editing the unit file
4. Fix the unit file → `systemctl daemon-reload` → `systemctl start tomcat` → verify again.

# 🧠 SECTION 3: MENTAL COMPRESSION MAP

## Core Problem → Solution Chain

```
Manual process (startup.sh / kill PID)
    │
    Problems:
    ├── No boot persistence (no enable)
    ├── No standard interface (automation tools fail)
    └── Complex stop procedure (find PID, kill, handle forks)
    │
    Solution: Write a systemd unit file
    │
    Result: systemctl start/stop/enable/status tomcat
```

## systemd Unit File Architecture

```
/etc/systemd/system/tomcat.service
    │
    ├── [Unit]           ← WHAT + WHEN
    │     ├── Description   (label)
    │     └── After         (ordering dependency)
    │
    ├── [Service]        ← HOW
    │     ├── Type          (forking = child process model)
    │     ├── User/Group    (runtime identity)
    │     ├── WorkingDirectory
    │     ├── Environment   (app-specific vars, not systemd vars)
    │     ├── ExecStart     (THE command behind "systemctl start")
    │     └── ExecStop      (THE command behind "systemctl stop")
    │
    └── [Install]        ← BOOT BEHAVIOR
          └── WantedBy    (multi-user.target = normal server mode)
```

## File Location Pattern

```
Package-managed services  →  /usr/lib/systemd/system/<name>.service  (auto-created)
Custom/manual services    →  /etc/systemd/system/<name>.service      (you create)

File name = service name:  tomcat.service → systemctl * tomcat
```

## Tomcat Deployment Flow

```
1. wget tarball → tar extract → raw folder with bin/, conf/, lib/...
2. dnf install java-17-openjdk (dependency)
3. useradd tomcat (--home-dir /opt/tomcat --shell /sbin/nologin)
4. cp -r extracted/* → /opt/tomcat/
5. chown -R tomcat.tomcat /opt/tomcat/
6. vim /etc/systemd/system/tomcat.service → write unit file
7. systemctl daemon-reload
8. systemctl start tomcat → status → enable
```

## Critical Wiring Map

```
ExecStart ──points to──► /opt/tomcat/bin/startup.sh
    │
    needs:
    ├── JAVA_HOME → /usr/lib/jvm/jre (Java must be installed here)
    ├── CATALINA_HOME → /opt/tomcat  (Tomcat's own locator)
    └── User=tomcat must OWN /opt/tomcat (chown -R)

Break any link → service fails
```

## Security Pattern

```
Service user: tomcat
    ├── --shell /sbin/nologin  → cannot SSH in
    ├── Owns only /opt/tomcat  → minimal privilege
    └── Service runs as this user → compromised service ≠ compromised root
```

## State Transition: Manual Process → Managed Service

```
BEFORE (manual):
    start  → ./bin/startup.sh
    stop   → ps -ef | grep tomcat → kill <PID> (+ children)
    enable → impossible
    status → ps -ef | grep tomcat (manual check)

AFTER (systemd):
    start  → systemctl start tomcat
    stop   → systemctl stop tomcat (handles children)
    enable → systemctl enable tomcat (boot persistence)
    status → systemctl status tomcat (structured output)
```

## daemon-reload Rule

```
Create/edit unit file → systemctl daemon-reload → THEN start/stop/enable
                         │
                         └── systemd caches unit files at boot
                             changes invisible until reload
```

## Automation Integration (DevOps)

```
Ansible service module:
    name: tomcat
    state: started
        │
        └──► calls systemctl start tomcat on target
                │
                └──► reads /etc/systemd/system/tomcat.service
                        │
                        └──► executes ExecStart

No unit file → Ansible fails → no standard management → not DevOps-ready
```

## Reusable Engineering Patterns

| Pattern                                      | Instance                                                                 |
| -------------------------------------------- | ------------------------------------------------------------------------ |
| **Standard interface contract**              | systemd unit file = universal service API for all tools                  |
| **Dedicated service user**                   | `tomcat` user: nologin, minimal ownership, non-root execution            |
| **Config-driven behavior**                   | Unit file maps `start`→`ExecStart`, `stop`→`ExecStop`                    |
| **Cache-then-reload**                        | systemd caches config at boot; `daemon-reload` forces re-read            |
| **Template-and-adapt**                       | Never write from scratch; copy existing unit file, modify paths/vars     |
| **Dependency ordering**                      | `After=network.target` = declarative "start me after X"                  |
| **Separation: app config vs. system config** | Environment vars = Tomcat's needs; Unit file structure = systemd's needs |
| **Package-managed vs. manual**               | dnf = everything auto-created; manual = you build the integration layer  |

## One-Line Recall Triggers

* **"What does ExecStart do?"** → It's the actual command `systemctl start` executes
* **"Why daemon-reload?"** → systemd caches unit files; reload forces re-read from disk
* **"Why a tomcat user?"** → Non-root security; nologin prevents interactive access
* **"Where do custom unit files go?"** → `/etc/systemd/system/<name>.service`
* **"What's Type=forking?"** → startup.sh forks a child Java process and exits
* **"Why not just use startup.sh?"** → No boot enable, no standard interface, manual PID killing
* **"WantedBy=multi-user.target?"** → Start this service in normal (non-GUI) server boot mode
