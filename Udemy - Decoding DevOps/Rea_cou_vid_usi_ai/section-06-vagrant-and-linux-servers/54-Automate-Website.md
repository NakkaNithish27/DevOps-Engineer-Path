## 1.1 The Core Problem — Why Automate a Manual Setup?

In the previous lectures of this course, two things were set up manually: a finance website on CentOS (installing Apache, downloading a template, deploying files) and a WordPress blog on Ubuntu. Each setup required logging into the VM via SSH, typing commands one by one, waiting, verifying, and fixing mistakes in real time. The setup worked, but it has a fundamental flaw — **it is trapped in the operator's hands and memory.** If you destroy the VM, the entire setup is gone. If you want to recreate it, you must remember every command, every path, every flag, and execute them again in the correct order. If a colleague needs the same environment, you must write instructions or sit next to them. [\[54-automat...site-setup \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/54-automate-website-setup.txt)

This lecture solves that problem by moving **every manual command into the Vagrantfile itself.** When you run `vagrant up`, Vagrant not only creates the VM and configures its resources (as covered in the previous lecture on IP/RAM/CPU), but also **executes those commands automatically inside the VM after boot.** This capability is called **provisioning.** [\[54-automat...site-setup \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/54-automate-website-setup.txt)

## 1.2 Infrastructure as Code (IaC) — The Concept

The instructor introduces the term **Infrastructure as Code (IaC)** — sometimes written as IAAC (Infrastructure Automation as Code). The idea is this: your entire infrastructure — the VM, its networking, its resources, *and the software/services/websites running on it* — is defined in a single text file (the Vagrantfile). That file is code. It can be versioned, copied, shared, and re-executed. [\[54-automat...site-setup \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/54-automate-website-setup.txt)

This is a paradigm shift from "infrastructure as manual work" to "infrastructure as a reproducible artifact." The Vagrantfile becomes the **single source of truth** for the complete environment. As long as you have that file, you can destroy the VM, move to a different machine, and recreate the identical environment by running one command. [\[54-automat...site-setup \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/54-automate-website-setup.txt)

The instructor frames it clearly: *"Our entire infrastructure, the website, will be in just one file, it will be code based. This is called infrastructure as code."* He also notes this is a basic introduction — the concept of IaC will be covered in much more detail later in the course, and the same provisioning scripts will be reused in AWS. [\[54-automat...site-setup \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/54-automate-website-setup.txt)

🔍 **Deep Dive:** IaC is not just about convenience. It enables **reusability** (the same file deploys the same environment anywhere), **consistency** (no human deviation between setups), **auditability** (you can see exactly what will be deployed by reading the file), and **disposability** (VMs become cheap to create and destroy because rebuilding is trivial). The instructor explicitly calls out reusability: *"Anytime you want to set up the website, you have the scripts with you, you can anywhere, anytime, set up this website."* [\[54-automat...site-setup \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/54-automate-website-setup.txt)

## 1.3 Vagrant Provisioning — The Mechanism

Vagrant provisioning is the feature that allows you to define commands (or scripts) inside the Vagrantfile that Vagrant will execute **inside the guest VM** after it boots. The default Vagrantfile generated by `vagrant init` already contains a commented-out provisioning block. You uncomment it and fill in your commands. [\[54-automat...site-setup \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/54-automate-website-setup.txt)

The provisioning block uses a shell provisioner by default. Each line you write is a shell command that runs as if you typed it directly inside the VM's terminal. Vagrant handles the SSH connection, command execution, and output streaming — you just define *what* to run. [\[54-automat...site-setup \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/54-automate-website-setup.txt)

The provisioning runs **after** the VM is created and booted, and **after** networking and resource settings are applied. This ordering matters — your provisioning commands may depend on network connectivity (e.g., downloading files from the internet), which requires the network adapters to be up first. [\[54-automat...site-setup \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/54-automate-website-setup.txt)

⚠️ **Expert Note:** There are two distinct failure modes during provisioning. A **syntax error** (typo in a command, wrong path, missing flag) will cause the provisioning to fail and stop — you'll see the error in the terminal output. A **logical error** (commands run successfully but produce the wrong result — e.g., files copied to the wrong directory) will *not* cause provisioning to fail. The VM will come up, provisioning will report success, but the website won't work correctly. The instructor explicitly warns about both: *"If you make any syntax error, this will fail. If you make any logical mistakes, the provisioning will go, but you might not be able to access the website."* This is a critical distinction — **provisioning success ≠ deployment correctness.** [\[54-automat...site-setup \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/54-automate-website-setup.txt)

## 1.4 The "Manual First" Rule — An Engineering Principle

Before writing any automation, the instructor enforces a rule: **you must know how to do it manually first.** The entire provisioning script is simply the sequence of manual commands from the previous lectures, placed into the Vagrantfile in the exact same order. [\[54-automat...site-setup \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/54-automate-website-setup.txt)

This is not just pedagogical advice — it is a practical engineering principle. If you try to automate something you don't fully understand manually, you won't know what the correct output looks like, you won't be able to debug failures, and you won't recognize logical errors. Manual execution gives you the **mental model of the process** that you then encode into automation. ## 1.5 Non-Interactive Execution — The `-y` Constraint

When you run commands manually in a terminal, some commands ask for confirmation: "Do you want to continue? \[y/N]." You type `y` and press Enter. In provisioning, there is no human sitting at the terminal. If a command prompts for input, the provisioning **hangs and eventually fails** because there is no one to respond. [\[54-automat...site-setup \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/54-automate-website-setup.txt)

This is why the `-y` flag is critical on commands like `yum install`. The `-y` flag pre-answers "yes" to all confirmation prompts, making the command fully non-interactive. The same principle applies to the `-o` flag on `unzip` — if a file already exists and `unzip` asks whether to overwrite, the provisioning will stall. The `-o` flag forces overwrite without asking. [\[54-automat...site-setup \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/54-automate-website-setup.txt)

The general rule: **every command in a provisioning script must be fully non-interactive.** Any command that could potentially prompt for user input must have its auto-confirm flag set. [\[54-automat...site-setup \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/54-automate-website-setup.txt)

🔍 **Deep Dive:** This non-interactive constraint applies not just to Vagrant provisioning but to *any* automated execution context — shell scripts, CI/CD pipelines, Docker builds, Ansible playbooks, cloud-init scripts. The pattern is universal: **automation requires deterministic, prompt-free execution paths.** [\[54-automat...site-setup \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/54-automate-website-setup.txt)

## 1.6 Idempotency Considerations — Safe Re-Provisioning

The instructor builds several safeguards into the provisioning script that address what happens if provisioning runs **more than once** (e.g., you run `vagrant provision` again, or `vagrant up` on a VM that already exists).

**`mkdir -p`:** The `-p` flag means "create the directory if it doesn't exist, but do not fail if it already exists." Without `-p`, running `mkdir /tmp/finance` a second time would produce an error ("directory already exists") and break the provisioning. With `-p`, the command is **idempotent** — it produces the same result regardless of how many times you run it. [\[54-automat...site-setup \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/54-automate-website-setup.txt)

**`unzip -o`:** The `-o` flag forces overwrite of existing files without prompting. This ensures re-provisioning replaces old files with fresh ones instead of stalling on a confirmation prompt. [\[54-automat...site-setup \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/54-automate-website-setup.txt)

These are not random flag choices — they represent the engineering principle of **idempotent operations**: operations that can be safely repeated without changing the outcome or causing errors. [\[54-automat...site-setup \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/54-automate-website-setup.txt)

## 1.7 The Cleanup Pattern — Don't Cut the Branch You're Sitting On

After downloading, unzipping, and copying the website files, the temporary directory (`/tmp/finance`) is no longer needed. The instructor adds a cleanup step to remove it. But there is a subtlety: the provisioning script had earlier run `cd /tmp/finance` to enter that directory. If you try to `rm -rf /tmp/finance` while your current working directory *is* `/tmp/finance`, you are — as the instructor vividly describes — *"cutting the same branch of the tree on which you are sitting."* [\[54-automat...site-setup \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/54-automate-website-setup.txt)

The solution: first `cd /tmp` (move out of the directory), then delete it. This is a classic shell scripting pitfall. The working directory is a reference the shell holds to a filesystem location. Deleting that location while you're in it creates undefined behavior on some systems or at minimum produces confusing errors. [\[54-automat...site-setup \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/54-automate-website-setup.txt)

## 1.8 The Provisioning Command Sequence — Why This Order?

The commands in the provisioning script follow a specific logical order that mirrors the manual setup. Understanding *why* this order exists is important:

1. **Install packages** (`yum install httpd wget unzip vim -y`) — you need the web server (httpd) and tools (wget for downloading, unzip for extracting, vim for optional editing) before you can do anything else. [\[54-automat...site-setup \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/54-automate-website-setup.txt)
2. **Start and enable the service** (`systemctl start httpd`, `systemctl enable httpd`) — the web server must be running before you deploy content (some templates or configurations may depend on httpd's directory structure being initialized). `enable` ensures httpd starts automatically on future reboots. [\[54-automat...site-setup \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/54-automate-website-setup.txt)
3. **Create a temporary working directory** (`mkdir -p /tmp/finance`) — a clean workspace for downloading and extracting files, separate from the web server's document root. [\[54-automat...site-setup \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/54-automate-website-setup.txt)
4. **Download the template** (`wget <URL>`) — fetches the zip file from tooplate.com into the temp directory. [\[54-automat...site-setup \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/54-automate-website-setup.txt)
5. **Extract** (`unzip -o <zipfile>`) — unpacks the template files. [\[54-automat...site-setup \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/54-automate-website-setup.txt)
6. **Copy to web root** (`cp -r <template_folder>/* /var/www/html/`) — deploys the extracted files to Apache's document root where they become servable. [\[54-automat...site-setup \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/54-automate-website-setup.txt)
7. **Restart the service** (`systemctl restart httpd`) — ensures Apache picks up the new content. [\[54-automat...site-setup \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/54-automate-website-setup.txt)
8. **Cleanup** (`cd /tmp`, `rm -rf /tmp/finance`) — removes the temporary directory. [\[54-automat...site-setup \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/54-automate-website-setup.txt)

Each step depends on the one before it. You cannot unzip before downloading. You cannot copy before unzipping. You cannot serve before copying. This is a **sequential dependency chain** — the most common structure in provisioning scripts. [\[54-automat...site-setup \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/54-automate-website-setup.txt)

## Step 5: Write the Provisioning Commands

Replace the placeholder content between `<<-SHELL` and `SHELL` with the following commands, in this exact order:

### 5a. Install Required Packages

```bash
yum install httpd wget unzip vim -y
```

* `yum install` — the CentOS/RHEL package manager command to install software.
* `httpd` — the Apache web server.
* `wget` — command-line tool for downloading files from URLs.
* `unzip` — tool for extracting `.zip` archives.
* `vim` — text editor (useful for any manual debugging later).
* `-y` — **critical flag** — automatically answers "yes" to all prompts. Without this, provisioning will hang waiting for input and eventually fail. [\[54-automat...site-setup \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/54-automate-website-setup.txt)

### 5b. Start and Enable Apache

```bash
systemctl start httpd
systemctl enable httpd
```

* `systemctl start httpd` — starts the Apache service immediately.
* `systemctl enable httpd` — configures Apache to start automatically on every future boot of the VM.
* Two separate commands because `start` affects the current session and `enable` affects future boots — they are independent operations. [\[54-automat...site-setup \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/54-automate-website-setup.txt)

### 5c. Create a Temporary Working Directory

```bash
mkdir -p /tmp/finance
```

* `mkdir` — create directory.
* `-p` — "parents" flag — creates the directory if it doesn't exist, and **does not fail** if it already exists. This makes the command safe for repeated provisioning (idempotent, as discussed in Theory §1.6). [\[54-automat...site-setup \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/54-automate-website-setup.txt)

### 5d. Navigate into the Temporary Directory

```bash
cd /tmp/finance
```

Changes the working directory so that subsequent commands (wget, unzip) operate inside this temp folder. [\[54-automat...site-setup \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/54-automate-website-setup.txt)

### 5e. Download the Template

```bash
wget <URL_of_zip_file>
```

Replace `<URL_of_zip_file>` with the actual download URL from tooplate.com.

**How to get the URL** (as taught in Theory §1.9):

1. Go to tooplate.com in your browser.
2. Select the template you want.
3. On the template page, press **F12** → go to the **Network** tab.
4. Click the **Download** button on the page.
5. A new entry appears in the Network tab — click on it.
6. Go to **Headers** → copy the **Request URL** (this is the direct `.zip` URL). [\[54-automat...site-setup \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/54-automate-website-setup.txt)

Paste this URL after `wget`.

### 5f. Unzip the Downloaded File

```bash
unzip -o <zipfilename>.zip
```

* `unzip` — extracts the archive.
* `-o` — **overwrite without prompting.** Essential for non-interactive execution (same principle as `-y` on yum). If files already exist from a previous provisioning run, `-o` ensures they are silently replaced. [\[54-automat...site-setup \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/54-automate-website-setup.txt)
* `<zipfilename>.zip` — use the exact filename of the zip you downloaded (matches the last part of the URL).

### 5g. Copy Extracted Files to Apache's Document Root

```bash
cp -r <zipfilename>/* /var/www/html/
```

* `cp` — copy command.
* `-r` — recursive — copies all files and subdirectories.
* `<zipfilename>/*` — when you unzip, a folder with the same name as the zip (minus `.zip`) is created. The `/*` selects everything inside that folder.
* `/var/www/html/` — Apache's default document root. Any files placed here are served by the web server. [\[54-automat...site-setup \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/54-automate-website-setup.txt)

**Common mistake:** Forgetting to remove `.zip` from the folder name. The zip file is `template.zip`, but the extracted folder is `template/` (no `.zip`). Make sure the `cp` source path uses the folder name without `.zip`. [\[54-automat...site-setup \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/54-automate-website-setup.txt)

### 5h. Restart Apache

```bash
systemctl restart httpd
```

Restarts Apache to ensure it picks up the newly deployed content. [\[54-automat...site-setup \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/54-automate-website-setup.txt)

### 5i. Cleanup — Remove the Temporary Directory

```bash
cd /tmp
rm -rf /tmp/finance
```

* `cd /tmp` — **move out** of the `/tmp/finance` directory first. This is essential — you cannot safely delete a directory while your working directory is inside it (see Theory §1.7). [\[54-automat...site-setup \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/54-automate-website-setup.txt)
* `rm -rf /tmp/finance` — removes the temporary directory and all its contents.
  * `-r` — recursive (delete directory and everything inside).
  * `-f` — force (don't prompt for confirmation).

*Connection to flow:* The provisioning script is now complete. Every command that was previously executed manually is captured in the Vagrantfile. [\[54-automat...site-setup \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/54-automate-website-setup.txt)

# 🧠 SECTION 3: MENTAL COMPRESSION MAP

***

## 3.1 System Architecture — Automated Website Deployment

```
Vagrantfile (single file = entire infrastructure)
│
├── VM Config: box, network (private IP), RAM, CPU
│
└── Provisioning Block (shell commands executed inside VM post-boot)
    │
    ├── Install: yum install httpd wget unzip vim -y
    ├── Start:   systemctl start httpd
    ├── Enable:  systemctl enable httpd
    ├── Workspace: mkdir -p /tmp/finance → cd /tmp/finance
    ├── Download:  wget <template_zip_URL>
    ├── Extract:   unzip -o <file>.zip
    ├── Deploy:    cp -r <folder>/* /var/www/html/
    ├── Restart:   systemctl restart httpd
    └── Cleanup:   cd /tmp → rm -rf /tmp/finance
```

***

## 3.2 Provisioning Command Dependency Chain

```
yum install (tools exist)
    → systemctl start/enable (service running)
        → mkdir -p (workspace ready)
            → cd (in workspace)
                → wget (file downloaded)
                    → unzip -o (files extracted)
                        → cp -r (files in web root)
                            → systemctl restart (service reloaded)
                                → cd /tmp → rm -rf (cleanup)
```

**Each step depends on the previous. Strict sequential execution. No parallelism.**

***

## 3.3 Non-Interactive Execution Flags

```
Command      Flag    Purpose
─────────    ────    ───────────────────────────────────
yum install  -y      Auto-confirm install prompts
mkdir        -p      No-fail if directory exists
unzip        -o      Overwrite files without asking
rm           -rf     Force-remove, no confirmation
```

**Pattern:** Every flag exists to prevent the command from prompting for human input or failing on repeated runs.

***

## 3.4 The IaC Lifecycle

```
MANUAL SETUP (learn & verify)
       │
       ▼
ENCODE into Vagrantfile (provisioning block)
       │
       ▼
vagrant up (create + boot + provision → working website)
       │
       ▼
TEST (browser → http://<VM_IP>)
       │
       ▼
vagrant destroy (VM gone, Vagrantfile survives)
       │
       ▼
REUSE: vagrant up again (identical environment recreated)
       │
       ▼
PORTABILITY: same commands → AWS user-data / Docker / Ansible
```

***

## 3.5 Failure Mode Map

```
Failure Type        Symptom                      Detection
──────────────      ─────────────────────        ──────────────────
Syntax error        Provisioning stops,          Error in terminal output
                    error printed                during vagrant up

Logical error       Provisioning completes,      Website doesn't load;
                    no error shown               SSH in → inspect files/service

IP collision        Network error at boot        Change last octet in Vagrantfile

Stale .vagrant      Vagrant links to wrong VM    Delete .vagrant folder
folder                                           in copied directory

Missing -y/-o       Provisioning hangs           Add non-interactive flags
                    (waiting for input)
```

***

## 3.6 File/Path Reference Map

```
/var/www/html/          ← Apache document root (deploy files here)
/tmp/finance/           ← Temporary workspace (download + extract here)
<zipname>.zip           ← Downloaded archive filename
<zipname>/              ← Extracted folder (same name, no .zip)
<zipname>/*             ← All contents inside extracted folder
Vagrantfile             ← Single source of truth (IaC artifact)
.vagrant/               ← VM metadata folder (delete when cloning)
```

```
Browser → Template page → F12 (DevTools) → Network tab
    → Click "Download" button on page
        → New request appears in Network list
            → Click request → Headers tab → Request URL
                → Copy URL → paste into wget command
```

## 3.8 The Cleanup Anti-Pattern

```
WRONG:                          RIGHT:
cd /tmp/finance                 cd /tmp/finance
... (do work) ...               ... (do work) ...
rm -rf /tmp/finance  ← FAIL    cd /tmp             ← EXIT FIRST
(deleting your own CWD)         rm -rf /tmp/finance ← SAFE
```

**Mental model:** "Step off the branch before cutting it."
