## 1.1 — The Problem: Database Administration is Hard

Before understanding RDS, you must understand the burden it eliminates. Running a database in production involves a **massive operational surface area**: setting up the database software, performing **regular patching** (security and version updates), **continuous monitoring** of database health and performance, **performance tuning** (query optimization, index management), **regular backups** (because losing customer data is "extremely bad for the business"), **scaling** (adding more capacity as the business grows — which is particularly difficult for SQL databases), **security** management (to prevent data breaches — "you hear a lot of stories every now and then, some website data was put on the Black Market"), **hardware upgrades**, and **storage management** (scaling disk space as data grows). [\[131. RDS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/131.%20RDS.txt)

That's at least eight distinct operational responsibilities, each requiring specialized knowledge. A traditional database setup means you manage all of this yourself — the infrastructure, the software, the backups, the security, the scaling. Every one of these is a potential failure point.

***

## 1.2 — What RDS Is and What It Solves

**Amazon RDS (Relational Database Service)** is a **managed distributed relational database service**. The key word is **managed** — AWS handles most of the operational burden described above: automated backups, automated patching, monitoring, hardware management, storage scaling, high availability setup. You focus on using the database; AWS focuses on running it. [\[131. RDS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/131.%20RDS.txt)

RDS is a **Platform as a Service (PaaS)** for databases. The instructor explicitly highlights this distinction: "The RDS instance is a Platform as a Service." This means there is **no operating system to log into** — you don't SSH into an RDS instance. You don't manage the OS, install packages, or check OS-level logs directly. You interact with the database through its endpoint (connection string) using database client tools. OS-level logs are streamed to **CloudWatch** if needed. [\[131. RDS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/131.%20RDS.txt)

> 🔍 **Deep Dive:** This PaaS nature is a fundamental architectural difference from running a database on an EC2 instance (which would be IaaS — you manage everything from the OS up). With RDS, the abstraction layer removes the OS entirely from your responsibility. The tradeoff: less control (you can't tune kernel parameters, install custom OS packages, or access the filesystem directly) but dramatically less operational burden. For most workloads, this tradeoff is heavily favorable toward RDS.

***

## 1.3 — Supported Database Engines

RDS supports **six database engines**, each serving different project requirements:

* **MySQL** — Open source, widely used, free tier available.
* **PostgreSQL** — Open source, advanced features, popular for complex workloads.
* **MariaDB** — MySQL fork, open source, community-driven.
* **Oracle Database** — Commercial, enterprise-grade.
* **Microsoft SQL Server** — Commercial, common in Windows/.NET ecosystems.
* **IBM Db2** — Newest addition to RDS. [\[131. RDS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/131.%20RDS.txt)

You select the engine based on your **project requirements** — what the application was built for, what the team knows, what licensing the organization has.

### Amazon Aurora — The AWS-Native Engine

**Aurora** deserves special attention. It's not a separate engine in the traditional sense — you create Aurora in either **MySQL-compatible** or **PostgreSQL-compatible** mode. If you already know MySQL or PostgreSQL, you can use Aurora with the same query syntax and tools. [\[131. RDS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/131.%20RDS.txt)

Aurora's claimed advantages (from AWS documentation):

* **1/10th the cost** of commercial databases (no licensing overhead)
* **5x throughput** of standard MySQL
* **3x throughput** of standard PostgreSQL
* Better scaling capabilities for SQL databases (traditionally a major challenge)
* **Aurora Serverless** — auto-scales compute capacity, you pay per request [\[131. RDS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/131.%20RDS.txt)

Aurora is an AWS-exclusive service — you won't find it on other cloud providers. It represents AWS's attempt to solve the fundamental difficulty of scaling relational databases.

## 1.4 — High Availability: Multi-AZ Deployments

RDS provides built-in **high availability** through **Multi-AZ (Multi-Availability Zone)** deployments. There are two Multi-AZ configurations: [\[131. RDS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/131.%20RDS.txt)

### Multi-AZ DB Instance

One **primary** database instance and one **standby** instance, each in a **different Availability Zone**. Under normal operation, all traffic goes to the primary. The standby continuously replicates data from the primary but doesn't serve any traffic. If the primary fails, the standby **automatically takes over** — it becomes the new primary and starts handling both read and write requests. This is **automatic failover** for disaster recovery. [\[131. RDS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/131.%20RDS.txt)

### Multi-AZ DB Cluster

One **primary** instance and **two readable standby** instances, each in different AZs. The key difference from the DB Instance model: the standbys **also serve read queries**. Read traffic is distributed across the standbys, reducing load on the primary. If the primary fails, one standby is promoted. This gives you both **high availability AND read performance improvement**. [\[131. RDS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/131.%20RDS.txt)

### Single DB Instance

One database instance with no standby. No automatic failover. Used for development, testing, and free tier usage. [\[131. RDS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/131.%20RDS.txt)

## 1.5 — Read Replicas: Performance Optimization

Separate from Multi-AZ (which is about **availability**), **Read Replicas** are about **performance**. A read replica is a copy of your primary database that continuously syncs data from the primary. It gets its own **endpoint** (connection URL). Developers configure their application so that **read requests** (SELECT queries) go to the read replica endpoint, while **write requests** (INSERT, UPDATE, DELETE) go to the primary. [\[131. RDS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/131.%20RDS.txt)

This dramatically improves performance because "most of the requests on the DB will be read, in most of the applications." By offloading read traffic to replicas, the primary handles less load and can process writes faster.

> 🔍 **Deep Dive:** Multi-AZ and Read Replicas solve different problems and can be used together. Multi-AZ = "what happens if my database server dies?" (availability). Read Replica = "my database is slow because too many queries hit it" (performance). Multi-AZ standbys don't serve traffic in the DB Instance model; read replicas always serve read traffic. In a Multi-AZ DB Cluster, the standbys serve reads — blending both concepts.

***

## 1.6 — The Common Architecture: Private RDS + Public EC2

The most common RDS deployment pattern: RDS is created **within your VPC** (Virtual Private Cloud) as a **privately accessible** instance — it cannot be accessed from the Internet. An EC2 instance in the same VPC runs the web application and accesses RDS **privately** over the internal network. Users access the EC2 instance (the web server) from the Internet. The web server then connects to RDS internally. [\[131. RDS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/131.%20RDS.txt)

```
Internet → User → EC2 (web server, public) → RDS (database, private)
```

This is a security best practice: the database is never exposed to the Internet. Only authorized internal services can reach it.

***

## 1.7 — RDS Security: Security Groups and Authentication

Like all AWS network services, RDS requires a **security group**. The RDS security group must allow **inbound traffic on the database port** (e.g., 3306 for MySQL) from the security group of the instances that need to connect to it. This is the same **SG-to-SG referencing** pattern seen with EFS — you allow traffic from the EC2 instance's security group, not from specific IPs. [\[131. RDS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/131.%20RDS.txt)

**Authentication** can be done via:

* **Password authentication** — Traditional username/password (used in the video).
* **AWS Secrets Manager** — More secure; the password is stored and managed by AWS Secrets Manager. Not free.
* **IAM database authentication** — Uses IAM roles instead of passwords. [\[131. RDS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/131.%20RDS.txt)

> ⚠️ **Expert Note:** When RDS is created with auto-generated password, a popup shows the credentials **once**. If you miss it or lose it, you must reset the password. The instructor explicitly warns: "Make sure you save this username and password... once this is gone you cannot recover it. You have to reset then the password." Save it immediately — sticky note, password manager, whatever works. [\[131. RDS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/131.%20RDS.txt)

## 1.8 — RDS Configuration Options (Key Decisions)

### Instance Type

Same concept as EC2 instance types — determines CPU, RAM, and network capacity:

* **Standard classes** — General purpose (M series equivalent)
* **Memory optimized** — For high-performance databases (R and X series). Recommended for production.
* **Burstable classes** — Cost-effective for variable workloads (T series). `db.t3.micro` is **free tier eligible**. [\[131. RDS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/131.%20RDS.txt)

### Storage

* **gp3 / gp2** — General Purpose SSD. Good for most workloads.
* **Provisioned IOPS SSD** — High-performance storage for production databases with heavy I/O. Not free.
* **Magnetic** — Legacy, very slow. Only for standby/archive use, not real-time. [\[131. RDS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/131.%20RDS.txt)
* **Auto-scaling storage** — Automatically increases storage when nearing capacity. You set a maximum threshold.

### Backups

Automated backups take periodic snapshots and maintain transaction logs. You configure:

* **Retention period** — How many days to keep backups (1–35 days). Backups older than the retention period are automatically deleted.
* **Backup window** — When backups are taken (a scheduled time window). [\[131. RDS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/131.%20RDS.txt)

### Encryption

* **Encryption at rest** — Data stored on disk is encrypted. Uses AWS KMS (Key Management Service) for encryption keys.
* The instructor warns: **do not enable KMS encryption in free tier labs** — "You cannot delete the KMS keys also. You have to disable the key for, you know, it takes seven days to actually disable the key. So it's quite a hassle." [\[131. RDS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/131.%20RDS.txt)

### Logs

Since there's no OS to log into, MySQL service logs can be streamed to **Amazon CloudWatch Logs**. Four types of logs are available for streaming. [\[131. RDS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/131.%20RDS.txt)

### Maintenance

* **Auto minor version upgrade** — AWS can automatically apply minor version patches. Some organizations disable this because they don't want unplanned changes to their database.
* **Maintenance window** — A scheduled time window for upgrades and setting changes. This window is also used when you manually modify RDS settings and choose "apply during maintenance window" instead of "apply immediately." [\[131. RDS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/131.%20RDS.txt)

### Delete Protection

Prevents accidental deletion of the RDS instance. A safety guard for production databases.

### Initial Database Name

You can specify a database name (e.g., `accounts`) at creation time. This database is created automatically inside the RDS instance when it launches. [\[131. RDS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/131.%20RDS.txt)

## 1.9 — RDS Snapshots (Backups)

RDS supports both **automated backups** (configured at creation time with retention period and window) and **manual snapshots** (taken on-demand via the Actions menu). This mirrors the EBS snapshot concept — point-in-time backups that can be used for recovery. When deleting an RDS instance, it offers to take a **final snapshot** to preserve data before deletion. [\[131. RDS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/131.%20RDS.txt)

***

## 1.10 — Modifying an RDS Instance After Creation

RDS instances are **not static** — most settings can be changed after creation through the **Modify** option:

* Engine version (upgrades)
* Instance type (scale up/down)
* Storage (increase size, change type)
* Multi-AZ (convert single instance to Multi-AZ)
* Password reset
* Security group changes
* And more [\[131. RDS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/131.%20RDS.txt)

Changes can be applied **immediately** or during the **maintenance window**.

## Step 3: Configure the RDS Security Group

### What We're Doing

Allowing the EC2 client instance to connect to RDS on port 3306 by updating the RDS security group.

### The Action

1. Go to RDS → select your database → find the **Security Group** link → open it.
2. Click **Edit inbound rules.** [\[131. RDS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/131.%20RDS.txt)

### The Default Rule (Remove/Ignore)

By default, it may show 3306 allowed from "My IP" — this is useless because RDS is private (no public access). It can't be reached from the Internet.

### Add the Correct Rule

| Type         | Port | Source                                               |
| ------------ | ---- | ---------------------------------------------------- |
| MySQL/Aurora | 3306 | **The EC2 client's security group** (`rdssqlclient`) |

 [\[131. RDS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/131.%20RDS.txt)

### Why SG-to-SG

By referencing the EC2 instance's security group as the source, any instance in that security group can access RDS. No IP tracking needed. If you launch more client instances in the same SG, they automatically get access.

## 🔄 Availability & Performance Models

```
HIGH AVAILABILITY (Multi-AZ):
  ┌─────────────────────────────────────────────────┐
  │ Multi-AZ DB Instance                            │
  │   Primary (AZ-a) ←──replication──→ Standby (AZ-b) │
  │   All traffic → Primary                         │
  │   Primary fails → Standby auto-promotes          │
  ├─────────────────────────────────────────────────┤
  │ Multi-AZ DB Cluster                             │
  │   Primary (AZ-a) ←──replication──→ Standby-1 (AZ-b) │
  │                  ←──replication──→ Standby-2 (AZ-c) │
  │   Writes → Primary                              │
  │   Reads → Standbys (load distributed)            │
  │   Primary fails → Standby auto-promotes          │
  ├─────────────────────────────────────────────────┤
  │ Single DB Instance                              │
  │   One instance. No failover. Dev/test/free tier. │
  └─────────────────────────────────────────────────┘

PERFORMANCE (Read Replicas):
  Primary ←──continuous sync──→ Read Replica (own endpoint)
  App code: writes → primary endpoint
            reads  → replica endpoint
  WHY: Most DB traffic is reads → offload to replica → primary faster
```

## 🧩 Reusable Engineering Patterns

```
PATTERN 1: MANAGED SERVICE = OPERATIONAL BURDEN OFFLOAD
  Self-managed DB: you do patching, backups, monitoring, scaling, security, hardware
  RDS: AWS does it → you focus on data and application
  → Same as: EFS vs self-managed NFS, ELB vs self-managed load balancer,
    managed Kubernetes (EKS) vs self-managed K8s

PATTERN 2: PRIVATE SERVICE + PUBLIC GATEWAY
  Database = private (no Internet access)
  Web server = public (Internet-facing) → connects to DB privately
  → Same as: API backend + API gateway, microservice + ingress controller,
    any tiered architecture where data layer is internal-only

PATTERN 3: READ/WRITE SPLITTING (Read Replicas)
  Writes → primary | Reads → replica (separate endpoints)
  → Same as: CQRS pattern, read-optimized caches (Redis),
    CDN for static content, primary/secondary in any data system

PATTERN 4: AUTOMATIC FAILOVER (Multi-AZ)
  Primary fails → standby auto-promotes → zero manual intervention
  → Same as: database clustering, Redis Sentinel, K8s pod rescheduling,
    any active-passive HA setup with automatic promotion

PATTERN 5: SG-TO-SG ACCESS CONTROL (Recurring AWS Pattern)
  Service SG allows traffic FROM client SG (not IP-based)
  → Seen in: EFS (NFS from web SG), RDS (3306 from client SG)
  → Universal AWS pattern for private service access
```
