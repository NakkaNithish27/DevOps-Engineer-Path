## 1. What EBS Is — Virtual Hard Disks for EC2

EBS stands for **Elastic Block Store**. The instructor opens with the simplest possible definition: EBS volumes are **"really the virtual hard disks for your EC2 instance."** Every physical computer has a hard disk; every EC2 instance has EBS volumes. That's the one-to-one mapping. [\[118. EBS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/118.%20EBS.txt)

EBS provides two things:

* **EBS Volumes** — the virtual hard disks themselves.
* **Snapshots** — backups of EBS volumes (a full point-in-time copy of the volume's data).

EBS is **block-based storage** — meaning it works like a traditional hard disk at the block level. You can create partitions on it, format those partitions with a filesystem, and mount them to directories. This is fundamentally different from object storage (like S3) where you store files as objects. Block storage gives you the raw disk experience that operating systems expect. [\[118. EBS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/118.%20EBS.txt)

***

## 2. The Two Uses of EBS Volumes

EBS volumes serve two distinct purposes on an EC2 instance: [\[118. EBS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/118.%20EBS.txt)

**Root Volume (OS Storage):** When you launch an EC2 instance, the AMI is loaded onto an EBS volume that becomes the **root volume**. This is the volume you see during launch (e.g., 8 GB for Amazon Linux). It stores the operating system, system files, and by default, all your application data. The instructor calls this the "root volume" and points to the 8 GB volume visible in the EC2 launch wizard.

**Data Volume (Additional Storage):** You can attach **additional EBS volumes** to store other data — databases, web server files, images, logs, or any data you want to keep on a **separate disk** from the OS. This is exactly what the exercise does: creating a separate volume for website images.

The key engineering reason for separating OS and data onto different volumes is **isolation** — if you need to replace the OS (re-image the instance), your data volume is untouched. If the data volume fills up, the OS volume isn't affected. This is the same isolation principle from the containers lecture, applied at the storage level. [\[118. EBS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/118.%20EBS.txt)

## 3. The Availability Zone Constraint — The Critical Rule

When creating an EBS volume, you **must specify an availability zone**, and **your EC2 instance must be in the same zone as the EBS volume**. If your instance is in `us-east-1c`, your volume must also be in `us-east-1c`. You **cannot attach a volume from zone `1a` to an instance in zone `1c`**. [\[118. EBS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/118.%20EBS.txt)

The instructor explicitly warns about this and demonstrates checking the instance's zone before creating the volume. This is the single most common mistake when creating EBS volumes — creating it in the wrong zone and then being unable to attach it.

Within the availability zone, **EBS volume data is automatically replicated** — AWS replicates the data within the zone to protect against hardware failure at the data center level. But this replication is **within the same availability zone only**, not across multiple zones. For cross-zone protection, you use snapshots. [\[118. EBS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/118.%20EBS.txt)

<details>
<summary>🔍 Deep Dive</summary>

The availability zone constraint exists because EBS volumes are physically located in a specific data center (availability zone). Attaching a volume to an instance means creating a high-speed network link between the instance's compute hardware and the volume's storage hardware. This link only works within the same physical facility. Cross-zone attachment would require data to travel between data centers, introducing latency that would make block storage unusably slow. This is a fundamental physics constraint, not an arbitrary AWS limitation.

</details>

## 4. EBS Volume Types — Five Categories

The instructor covers five volume types, each designed for different performance and cost profiles: [\[118. EBS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/118.%20EBS.txt)

### General Purpose SSD (GP2 / GP3)

The **most recommended** type from AWS for general workloads. It's an SSD (Solid State Drive), providing good performance at reasonable cost. The instructor calls it **"the best combination of right pricing and right speed."** GP3 is the latest generation. Used for: web servers, development environments, small-to-medium databases, and most standard workloads. This is what the course uses. [\[118. EBS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/118.%20EBS.txt)

### Provisioned IOPS SSD

Used for workloads that need **very high I/O performance** — specifically **large databases**. The IOPS (Input/Output Operations Per Second) is significantly higher than General Purpose. You explicitly provision (request) a specific IOPS level, and AWS guarantees it. More expensive than General Purpose, but necessary when database performance is critical. [\[118. EBS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/118.%20EBS.txt)

### Throughput Optimized HDD

An HDD (Hard Disk Drive, not SSD) optimized for **high throughput** — large sequential reads/writes. Used for **big data, data warehouses, and log processing**. Not as fast for random I/O as SSDs, but excellent for streaming large volumes of data sequentially. [\[118. EBS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/118.%20EBS.txt)

### Cold HDD

Another HDD type designed for **infrequently accessed data** — large datasets that you store but don't read often. Used for **file servers** and cold storage. **Very low cost**. The instructor describes it as data that is "not so frequently accessed." [\[118. EBS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/118.%20EBS.txt)

### Magnetic (Previous Generation)

The **slowest and cheapest** option. Recommended for **backups and archives**. Maximum size of 1 TB. Very low IOPS. The instructor notes it's "very, very cheap." This is the legacy option — still available but superseded by the HDD types for most use cases. [\[118. EBS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/118.%20EBS.txt)

The instructor directs learners to the **AWS documentation** (searchable as "EBS volume types") for detailed specifications: volume sizes, IOPS numbers, throughput values, and use cases for each type. [\[118. EBS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/118.%20EBS.txt)

<details>
<summary>⚠️ Expert Note</summary>

The decision tree for volume type selection in production: Start with **GP3** (general purpose) as the default. If your workload is a database requiring guaranteed IOPS → **Provisioned IOPS SSD**. If you're processing large sequential data (big data, logs) → **Throughput Optimized HDD**. If you're storing large data accessed rarely → **Cold HDD**. If you're archiving/backing up and cost is the primary concern → **Magnetic**. GP3 handles 80%+ of real-world workloads.

</details>

## 5. EBS Volume Encryption

The instructor mentions that you can **encrypt an EBS volume** — this is called **"encryption at rest"**, meaning all data stored on the volume is encrypted on disk. To encrypt, you need an **encryption key**. AWS provides a **default encryption key** (free), or you can create a custom key using the **KMS (Key Management Service)** — but KMS keys are **not free**. [\[118. EBS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/118.%20EBS.txt)

The instructor doesn't use encryption in this lab but explicitly states: **"do remember you can encrypt an EBS volume"** — this is a requirement awareness point for production systems where data security compliance requires encryption at rest.

## 6. Volume States — Available vs In-Use

EBS volumes have two primary states: [\[118. EBS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/118.%20EBS.txt)

* **Available** — the volume exists but is **not attached** to any instance. It's sitting idle, ready to be connected.
* **In-use** — the volume is **attached** to an instance and actively serving as storage.

The instructor explicitly checks the volume state after creation to confirm it's "available" before attaching it.

## 7. Linux Disk Concepts — Partitions, Formatting, and Mounting

This section of the video bridges AWS (EBS volumes) with **core Linux system administration** — the actual OS-level operations needed to make a new disk usable. [\[118. EBS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/118.%20EBS.txt)

**Disks and Partitions:** A disk (EBS volume in AWS, physical hard disk in traditional systems) is a raw block device. Before you can store files on it, you must create **partitions** — logical divisions of the disk. A disk can have up to four **primary partitions**. The instructor notes: "first four partitions are primary."

**Formatting:** A raw partition has no filesystem — it's just a block of sectors. Before you can store files, you must **format** the partition with a filesystem. The instructor lists common filesystem types: **NTFS** (Windows), **FAT** (USB drives, pen drives), **ext2/ext4** (Linux, general purpose), **XFS** (Linux, large volumes, faster I/O), **MS-DOS**. The root volume uses **XFS**. For this lab, the instructor chooses **ext4** — described as "just like general purpose." [\[118. EBS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/118.%20EBS.txt)

**Mounting:** Even after formatting, a partition is not accessible as a directory. You must **mount** it — link the partition to a specific directory in the filesystem hierarchy. After mounting `/dev/xvdf1` to `/var/www/html/images`, any data written to that directory physically resides on the new EBS volume, not on the root volume.

**The Hiding Effect:** The instructor highlights a critical behavior: when you mount a partition to a directory **that already has data**, the existing data becomes **hidden** (not deleted). It still exists on the original partition, but the mount point now shows the new partition's content. When you **unmount**, the original data reappears. This is why the instructor moves the images to a temporary folder before mounting — to avoid them being hidden. [\[118. EBS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/118.%20EBS.txt)

**Temporary vs Permanent Mount:** The `mount` command creates a **temporary mount** — it lasts until the system reboots. For a **permanent mount** that survives reboots, you must add an entry to `/etc/fstab` (filesystem table). The `mount -a` command reads `/etc/fstab` and executes all entries. [\[118. EBS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/118.%20EBS.txt)

```bash
#!/bin/bash
yum install httpd wget unzip -y
systemctl start httpd
systemctl enable httpd
cd /tmp
wget https://www.tooplate.com/zip-templates/2119_gymso_fitness.zip
unzip -o 2119_gymso_fitness.zip
```

**Line-by-line:**

* `#!/bin/bash` — Shebang line: tells the system to use bash to execute this script.
* `yum install httpd wget unzip -y` — Installs Apache web server (`httpd`), `wget` (download tool), and `unzip` (extraction tool). `-y` auto-confirms prompts.
* `systemctl start httpd` — Starts the Apache service.
* `systemctl enable httpd` — Enables Apache to start automatically on boot.
* `cd /tmp` — Changes to the temporary directory (working space for downloads).
* `wget https://...2119_gymso_fitness.zip` — Downloads the website template ZIP file.
* `unzip -o 2119_gymso_fitness.zip` — Extracts the ZIP. `-o` overwrites existing files without prompting.
* `cp -r 2119_gymso_fitness/* /var/www/html/` — Copies all website files to Apache's document root. `-r` is recursive (includes subdirectories).
* `systemctl restart httpd` — Restarts Apache to serve the new content.

**Storage:** Keep default (8 GB GP3). Launch the instance. [\[118. EBS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/118.%20EBS.txt)

```bash
mount /dev/xvdf1 /var/www/html/images
```

* `mount` — Mounts a partition to a directory.
* `/dev/xvdf1` — The formatted partition.
* `/var/www/html/images` — The target mount point. [\[118. EBS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/118.%20EBS.txt)

**Verify:**

```bash
df -h
```

Now shows `/dev/xvdf1` mounted to `/var/www/html/images` with \~5 GB available. [\[118. EBS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/118.%20EBS.txt)

**Check website:** Refresh the browser → images are **missing** (the mounted volume is empty).

```bash
cp -r /tmp/img-backup/* /var/www/html/images/
```

**Connection to flow:** Data is on the new volume. But this mount is temporary — reboot will lose it.

## Step 11: Configure Permanent Mount via `/etc/fstab`

**What we are doing:** Adding an entry to the filesystem table so the mount survives reboots. [\[118. EBS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/118.%20EBS.txt)

**First, unmount the temporary mount:**

```bash
umount /var/www/html/images
```

**Verify it's unmounted:**

```bash
df -h
```

(The mount point should be gone.)

**Edit fstab:**

```bash
vi /etc/fstab
```

**Add the following line** (go to last line, press `o` to open new line in insert mode): [\[118. EBS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/118.%20EBS.txt)

```
/dev/xvdf1    /var/www/html/images    ext4    defaults    0 0
```

**Column breakdown:**

| Column | Value                  | Meaning                                               |
| ------ | ---------------------- | ----------------------------------------------------- |
| 1      | `/dev/xvdf1`           | Partition path                                        |
| 2      | `/var/www/html/images` | Mount point (directory)                               |
| 3      | `ext4`                 | Filesystem type (must match how you formatted it)     |
| 4      | `defaults`             | Mount options (standard defaults, no special options) |
| 5      | `0`                    | Dump flag (0 = don't dump/backup on crash)            |
| 6      | `0`                    | fsck flag (0 = don't run filesystem check on boot)    |

The instructor notes you can also use a **UUID** instead of the partition path (visible in existing fstab entries for the root partition). [\[118. EBS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/118.%20EBS.txt)

**Save and exit:** `Esc` → `:wq`

**Execute fstab entries:**

```bash
mount -a
```

* `mount -a` — Reads `/etc/fstab` and mounts all entries that aren't already mounted. [\[118. EBS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/118.%20EBS.txt)

**Verify:**

```bash
df -h
```

Shows `/dev/xvdf1` mounted to `/var/www/html/images`. The mount is now **permanent**. [\[118. EBS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/118.%20EBS.txt)

**Troubleshooting `mount -a` errors:** The instructor explicitly warns: if you get any error, check:

* Partition path is correct
* Directory path is correct
* Options spelling is correct
* No typographical errors

**Final step:**

```bash
systemctl restart httpd
```

**Connection to flow:** The entire EBS lifecycle is complete: create → attach → partition → format → mount (permanent) → serve data. [\[118. EBS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/118.%20EBS.txt)

<details>
<summary>⚠️ Expert Note</summary>

Using `/dev/xvdf1` in fstab is functional but fragile — device names can change if volumes are detached and reattached in different order. Production best practice is to use the **UUID** (Universally Unique Identifier) of the partition, which never changes. You can find the UUID with `blkid /dev/xvdf1` and use `UUID=<value>` in fstab instead of the device path.

</details>

# 🧠 SECTION 3: MENTAL COMPRESSION MAP

***

## Core Identity

```
TOPIC:   AWS EBS — Elastic Block Store (full lifecycle)
CONTEXT: AWS EC2 → storage layer → virtual hard disks
PURPOSE: Separate OS storage from data storage using dedicated EBS volumes
```

***

## What EBS Provides

```
EBS = Virtual Hard Disks for EC2
  ├── EBS VOLUME  = the disk itself (block storage)
  └── SNAPSHOT    = backup of a volume (point-in-time copy)
```

***

## Five Volume Types (Decision Tree)

```
GENERAL PURPOSE SSD (GP2/GP3)  ← DEFAULT choice, 80%+ workloads
  │                               Right price + right speed
  ├── PROVISIONED IOPS SSD     ← Large databases needing guaranteed high IOPS
  │
THROUGHPUT OPTIMIZED HDD       ← Big data, data warehouses, log processing (sequential)
  │
COLD HDD                       ← Infrequently accessed large data, file servers (cheapest HDD)
  │
MAGNETIC                       ← Backups/archives, slowest, cheapest, max 1TB (legacy)
```

***

## The Availability Zone Rule

```
EBS volume AZ === EC2 instance AZ    ← MUST MATCH or attachment fails
Data replicated WITHIN same AZ only  ← not cross-AZ
Cross-AZ protection                  → use Snapshots
```

***

## Volume States

```
AVAILABLE  → not attached, idle, ready
IN-USE     → attached to an instance, serving storage
```

***

## Full EBS Lifecycle (Operational Flow)

```
CREATE volume (AWS Console)
  ├── Choose type (GP3)
  ├── Choose size (5 GB)
  ├── Choose AZ (MUST match instance)
  ├── Optional: encrypt (default key = free, KMS key = paid)
  └── Tag meaningfully
       ↓
ATTACH to instance (Actions → Attach → select instance + device name)
       ↓ Volume state: available → in-use
SSH INTO INSTANCE
       ↓
VERIFY disk visible: fdisk -l → shows new disk
       ↓
PARTITION: fdisk /dev/xvdf → n → p → 1 → Enter → Enter → w
       ↓
FORMAT: mkfs.ext4 /dev/xvdf1
       ↓
PREPARE DATA: mkdir temp → mv existing data → clear mount point
       ↓
TEMPORARY MOUNT: mount /dev/xvdf1 /target/dir
       ↓
COPY DATA BACK: cp -r temp/* /target/dir/
       ↓
PERMANENT MOUNT: vi /etc/fstab → add entry → mount -a → verify with df -h
       ↓
RESTART SERVICE: systemctl restart httpd
```

***

## Linux Disk Operations Chain

```
RAW DISK (/dev/xvdf)
  → PARTITION (fdisk → /dev/xvdf1)
    → FORMAT (mkfs.ext4 → adds filesystem)
      → MOUNT (mount → links partition to directory)
        → DATA ACCESSIBLE at mount point

Without ANY step: disk is unusable at that level
```

***

## fdisk Interactive Commands

```
m  = help (show all commands)
n  = new partition
p  = print partition table
w  = write changes and exit
d  = delete partition
l  = list known partition types

Partition creation: n → p (primary) → 1 (number) → Enter (first sector) → Enter (last sector = full disk)
                    OR → +3G (specific size)
```

***

## Filesystem Types

```
ext4    ← Linux general purpose (used in this lab)
XFS     ← Linux large volumes, faster I/O (used for root volume)
NTFS    ← Windows
FAT/vfat← USB drives, pen drives
ext2    ← older Linux
```

***

## `/etc/fstab` Entry Format

```
/dev/xvdf1   /var/www/html/images   ext4   defaults   0   0
│            │                      │      │          │   │
partition    mount point            type   options    dump fsck
```

***

## The Mount Hiding Rule

```
Mount to directory WITH existing data:
  → existing data HIDDEN (not deleted)
  → mount shows new partition's content
  → umount → original data reappears

DEFENSE: move data to temp BEFORE mounting → copy back AFTER mounting
```

***

## Temporary vs Permanent Mount

```
TEMPORARY:  mount /dev/xvdf1 /path     → lost on reboot
PERMANENT:  /etc/fstab entry + mount -a → survives reboot

mount -a = read fstab → execute all entries
```

***

## Encryption

```
Encryption at rest = data encrypted on disk
  ├── Default AWS key  → FREE
  └── Custom KMS key   → PAID (KMS service charges)
Option exists during volume creation — not used in this lab
```

***

## Free Tier Awareness

```
EBS free tier: ≤ 30 GB total across all volumes
Root volume default: 8 GB (Linux) / 30 GB (Windows)
Lab volume: 5 GB → total 13 GB → within free tier
```

***

## Provisioning Script Pattern (from gymso.txt)

```
install packages → start service → enable on boot → download artifact → extract → deploy to webroot → restart
yum install      → systemctl start → systemctl enable → wget → unzip → cp -r → systemctl restart
```

***

## Reusable Engineering Patterns

```
1. OS/DATA SEPARATION        → Root volume = OS, data volume = application data
                                Isolation: replace OS without losing data, data growth doesn't crash OS

2. ZONE-AWARE PROVISIONING   → Resources must be in same AZ to interact
                                (applies to EBS+EC2, also to RDS, EFS, etc.)

3. RAW → STRUCTURED PIPELINE → Raw resource (disk) requires sequential transformation before use
                                disk → partition → format → mount (each step builds on previous)

4. TEMPORARY-THEN-PERMANENT  → Test with temporary mount → confirm working → make permanent in fstab
                                (same pattern: test config manually → then persist in config file)

5. TAG-EVERYTHING            → Meaningful names on every resource → findable at scale
                                Without tags: volume IDs are meaningless strings
```
