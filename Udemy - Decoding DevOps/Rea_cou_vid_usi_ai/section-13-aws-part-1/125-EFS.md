## 1.1 — The Core Problem: Why Block Storage Fails in Multi-Server Architectures

Before understanding EFS, you must understand the problem it solves. Consider a common production architecture: a website is hosted on **multiple web servers** behind a **load balancer**. Users access the load balancer, and the load balancer routes each request to one of the servers. This is the standard high-availability setup covered in earlier lectures. [\[125. EFS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/125.%20EFS.txt)

Now imagine users are **uploading images**. A user uploads an image. The load balancer routes that upload request to, say, **web01**. The image gets stored on **web01's hard disk** (its EBS volume — block storage). Later, the same user (or any user) accesses the site again. This time, the load balancer routes the request to **web02**. But web02's hard disk **doesn't have that image** — it was stored on web01's disk. The image is missing. The page is broken. [\[125. EFS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/125.%20EFS.txt)

This is the fundamental limitation of **block storage** (EBS, or any hard disk attached to a single computer). Block storage is **local to one machine**. An EBS volume can be connected to **only one instance at a time**. In a multi-server setup, each server has its own isolated storage. Files stored on one server's disk are invisible to every other server. [\[125. EFS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/125.%20EFS.txt)

The solution is **shared storage** — a centralized storage system that **all servers can access simultaneously**. Files that need to be shared across servers (images, videos, documents, user uploads, static assets) must live in a location that every server can read from and write to.

***

## 1.2 — The Shared Storage Concept: Centralized vs. Local

The architecture splits into two storage layers:

* **Block storage (local)** — Each server's own hard disk. This is where the **operating system**, the **application/service**, and any **server-specific data** reside. This stays as EBS.
* **Shared storage (centralized)** — A separate, network-accessible storage system where **files that need sharing** are stored. All servers mount this shared storage and can read/write to it simultaneously. [\[125. EFS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/125.%20EFS.txt)

In the Linux world, the most common shared storage protocol is **NFS (Network File System)**. To use NFS traditionally, you need to **host and manage an NFS server** — a dedicated machine with the storage disks, running the NFS daemon, handling client connections, managing backups, monitoring health. This is an **extra operational overhead** — another server to build, secure, monitor, patch, and maintain. [\[125. EFS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/125.%20EFS.txt)

***

## 1.3 — Amazon EFS: Managed NFS in the Cloud

**Amazon EFS (Elastic File System)** is AWS's answer to the shared storage problem. It is a **fully managed shared file system** hosted on AWS. You don't build an NFS server. You don't manage disks. You don't worry about capacity planning, replication, or server maintenance. You simply **create an EFS file system** and **mount it on your instances**. [\[125. EFS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/125.%20EFS.txt)

Key characteristics:

* **Shared** — Multiple EC2 instances can mount the same EFS file system simultaneously and read/write to it. This is the core difference from EBS (one instance at a time) vs. EFS (many instances at a time). [\[125. EFS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/125.%20EFS.txt)
* **Uses NFS protocol** — Under the hood, EFS speaks NFS. This means Linux instances need NFS client tools installed to communicate with it. The NFS port is **2049**.
* **Not limited to EC2** — EFS can be used from your on-premises data center as well, not only from AWS EC2 instances. [\[125. EFS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/125.%20EFS.txt)
* **Elastic** — The storage scales automatically. You don't pre-allocate size. It grows and shrinks with your data.
* **Regional** — By default, an EFS file system is available across **all Availability Zones** in the region. You can restrict it to one zone to save cost. [\[125. EFS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/125.%20EFS.txt)

> 🔍 **Deep Dive:** The distinction between EBS and EFS maps to two fundamental storage paradigms. **EBS = block storage** — raw disk blocks attached to one machine, like plugging a hard drive into a computer. **EFS = file storage** — a shared filesystem accessible over the network by many machines, like a network drive/share in an office. There's also a third paradigm (S3 = object storage), but that's not covered here. Understanding this three-tier storage model (block/file/object) is foundational to cloud architecture.

***

## 1.4 — EFS Security: The Security Group Requirement

EFS is a **network service** — instances connect to it over the network. Any network service on AWS needs a **security group** (firewall). The EFS security group must allow **inbound NFS traffic (port 2049)** from the security group of the instances that will mount it. [\[125. EFS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/125.%20EFS.txt)

This creates a **security group chain**: the web server instances belong to their own security group (e.g., `inner-peace-sg`). The EFS has its own security group (e.g., `inner-peace--sg`). The EFS security group's inbound rule allows NFS (port 2049) from the web server security group. This means only instances in the web server security group can access the EFS — not the entire Internet, not random instances, only the specific group you authorize. [\[125. EFS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/125.%20EFS.txt)

> 🔍 **Deep Dive:** Security group referencing (allowing traffic from another security group rather than an IP address) is a powerful AWS pattern. It means you don't need to track individual instance IPs. Any instance added to the web server security group automatically gains EFS access. Any instance removed loses access. The security boundary is defined by **group membership**, not by IP addresses. This scales cleanly — whether you have 2 instances or 200.

## 1.5 — EFS Access Points: The Connection Mechanism

To connect an EC2 instance to an EFS file system, the video uses **Access Points**. An access point is a connection entry point that links an instance to a specific EFS file system. You create an access point, associate it with your file system, and then reference both the file system ID and the access point ID when mounting. [\[125. There are multiple ways to access EFS (including IAM authorization), but the video specifically uses the **EFS Access Point** method.

## 1.6 — EFS Client Tools: Making Linux Understand EFS

A standard Linux OS doesn't natively understand EFS. To mount an EFS file system, you need to install the **`amazon-efs-utils`** package. This package provides the EFS mount helper — a tool that handles the NFS connection, TLS encryption, and authentication transparently. [\[125. EFS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/125.%20EFS.txt)

On Amazon Linux 2023:

```bash
yum install -y amazon-efs-utils
```

On other operating systems (Ubuntu, etc.), the package name or installation method differs — you'd search for "install Amazon EFS utils on \[OS name]" to find the appropriate instructions. The instructor also mentions `stunnel` as a dependency that may need installation. [\[125. EFS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/125.%20EFS.txt)

## 1.7 — The Mount Point as Transparent Redirection

This is the key architectural insight. The website has an **`images` folder** (e.g., `/var/www/html/images/`) that contains static images displayed on the web page. When the EFS file system is **mounted at this exact path**, the folder becomes a **transparent redirect** to the EFS storage. [\[125. EFS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/125.%20EFS.txt)

The web server (httpd/Apache) doesn't know or care that `/var/www/html/images/` is now on EFS instead of the local disk. It reads files from the path as usual. But the underlying storage is now **shared across all instances**. Any instance that mounts the same EFS at the same path sees the same files. Uploads go to EFS. Reads come from EFS. The local disk is completely bypassed for that directory. [\[125. EFS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/125.%20EFS.txt)

This is why the instructor **moves the images out** of the folder before mounting — because mounting EFS at that path **hides** whatever was on the local disk at that location. After mounting, the images are copied back — this time they go into the EFS file system, not the local disk.

***

## 1.8 — EFS Configuration Options

The video walks through several configuration options during EFS creation:

* **File system type: Regional** — Available across all AZs in the region. Choosing "One Zone" saves cost but limits availability. [\[125. EFS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/125.%20EFS.txt)
* **Automated backups** — Optional. Can be enabled for data protection (not used in the lab).
* **Lifecycle management / Transition to Archive** — Moves infrequently accessed data to cheaper archive storage after a configurable period (e.g., 30 days). Set to **"None"** in the lab. [\[125. EFS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/125.%20EFS.txt)
* **Encryption at rest** — EFS can store data encrypted on disk. Typically enabled in production.
* **Encryption in transit** — Encrypts data while traveling between instance and EFS. Separate from at-rest encryption.
* **Throughput mode: Bursting** — Scales throughput automatically when needed, stays lower otherwise. Saves cost vs. "Enhanced" mode which provides consistent high throughput. [\[125. EFS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/125.%20EFS.txt)
* **Performance mode: General Purpose** — Standard performance. "Max I/O" tolerates higher latencies and is for extreme workloads.
* **Subnet security groups** — Each AZ's subnet mount target gets a security group. Replace the default security group with the **EFS-specific security group** created earlier. [\[125. EFS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/125.%20EFS.txt)

***

## 1.9 — Creating an AMI with EFS Mount Point

After the EFS is mounted and working, the instructor creates an **AMI (Amazon Machine Image)** of the instance. This AMI captures the instance's state including the `/etc/fstab` entry. When you launch a new instance from this AMI, it will **automatically mount the EFS file system on boot** because the fstab entry is baked into the image. [\[125. EFS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/125.%20EFS.txt)

This is the production pattern: configure EFS mount once → create AMI → launch any number of instances from that AMI → all automatically connect to the same shared storage. Combined with a load balancer, this creates a horizontally scalable web tier where every instance sees the same shared files.

## Step 7: Configure fstab for Automatic EFS Mounting

### What We're Doing

Adding an entry to `/etc/fstab` so the EFS file system is automatically mounted whenever the instance boots.

### Get the Mount Entry Format

From the AWS documentation (EFS → Mounting → Existing EC2 Linux Instance → Automatic Mounting → Using EFS Access Point), the fstab entry format is:

```
<file-system-id>:/ <mount-point> efs _netdev,noresvport,tls,accesspoint=<access-point-id> 0 0
```

 [\[125. EFS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/125.%20EFS.txt)

### Gather the IDs

* **File System ID** — Found in EFS Console → File Systems (e.g., `fs-0abc123def456`)
* **Access Point ID** — Found in EFS Console → Access Points (e.g., `fsap-0abc123def456`)
* **Mount Point** — `/var/www/html/images` (or your equivalent folder)

### Edit fstab

```bash
vim /etc/fstab
```

Go to the last line. Enter insert mode (`i`). Add a new line with the assembled entry:

```
fs-0abc123def456:/ /var/www/html/images efs _netdev,noresvport,tls,accesspoint=fsap-0abc123def456 0 0
```

Save and quit (`:wq`). [\[125. EFS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/125.%20EFS.txt)

### Verify Before Mounting

```bash
df -h
```

No EFS mount should appear yet.

### Mount

```bash
mount -a
```

**Breakdown:**

* `mount` — Mount command
* `-a` — Mount **all** filesystems defined in `/etc/fstab`. This reads the fstab file and mounts any entries not already mounted. [\[125. EFS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/125.%20EFS.txt)

### Verify After Mounting

```bash
df -h
```

The EFS file system should now appear as a mounted filesystem at `/var/www/html/images`. [\[125. EFS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/125.%20EFS.txt)

### Common Mistakes

* **Wrong file system ID or access point ID** — Mount will fail. Double-check both IDs.
* **EFS security group doesn't allow NFS from instance's security group** — Mount will hang or timeout.
* **`amazon-efs-utils` not installed** — The `efs` filesystem type in fstab won't be recognized.
* **Wrong mount point path** — Must match the actual images directory path.

# 🧠 SECTION 3: MENTAL COMPRESSION MAP

## 🏗️ The Shared Storage Problem

```
WITHOUT SHARED STORAGE:
  User uploads image → LB → web01 → stored on web01's disk
  User returns        → LB → web02 → web02's disk has NO image ❌

WITH SHARED STORAGE (EFS):
  User uploads image → LB → web01 → stored on EFS (shared)
  User returns        → LB → web02 → reads from EFS → image found ✅

RULE: Files needing multi-server access → shared storage (EFS)
      OS + app binaries → block storage (EBS)
```

 [\[125. EFS \| Txt\]](https://myoffice.accenture.com/personal/nakka_nithish_accenture_com/Documents/Microsoft%20Copilot%20Chat%20Files/125.%20EFS.txt)

## 📊 EBS vs. EFS — Core Distinction

```
              EBS (Block Storage)         EFS (File Storage)
              ──────────────────          ──────────────────
Attachment    ONE instance at a time      MANY instances simultaneously
Protocol      Block device (disk)         NFS (network filesystem)
Use case      OS, apps, DB data           Shared files (images, uploads, assets)
Scope         Single AZ                   Regional (all AZs) or One Zone
Sizing        Fixed (you specify)         Elastic (auto-grows/shrinks)
Port          N/A (block-level)           2049 (NFS)
AWS managed?  Volume = yes, NFS = no      Fully managed NFS
```

## ⚡ Complete Execution Sequence

```
 1. Create EFS Security Group (NFS 2049 from web server SG)
 2. Create EFS File System (Regional, Bursting, GP, replace default SG with EFS SG on all subnets)
 3. Create Access Point (link to file system)
 4. Launch web server instance (from launch template)
 5. SSH in → verify /var/www/html/images exists
 6. Add HTTP rule to SG → verify images in browser ✅
 7. mv images/* → /tmp/temp-images/         ← Empty the mount point
 8. Verify images GONE in browser ✅
 9. yum install -y amazon-efs-utils         ← Install EFS client
10. vim /etc/fstab → add EFS entry          ← fs-ID:/ /path efs _netdev,noresvport,tls,accesspoint=ap-ID 0 0
11. mount -a                                 ← Mount from fstab
12. df -h                                    ← Verify EFS mounted ✅
13. cp /tmp/temp-images/* → /var/www/html/images/  ← Restore images to EFS
14. systemctl restart httpd
15. Verify images BACK in browser ✅ (now from EFS)
16. Create AMI (inner-peace-EFS)            ← Bake fstab entry into image
17. Cleanup: terminate instance, KEEP EFS + Access Point + AMI
```

## 📐 fstab Entry Structure

```
<fs-id>:/  <mount-point>  efs  _netdev,noresvport,tls,accesspoint=<ap-id>  0  0
  │            │           │              │                                  │  │
  │            │           │              │                                  │  └── dump order
  │            │           │              │                                  └── fsck order
  │            │           │              ├── _netdev = wait for network before mounting
  │            │           │              ├── noresvport = don't use reserved ports
  │            │           │              ├── tls = encrypt in transit
  │            │           │              └── accesspoint = EFS access point ID
  │            │           └── filesystem type (requires amazon-efs-utils)
  │            └── local directory path (e.g., /var/www/html/images)
  └── EFS file system ID (e.g., fs-0abc123)
```

## 🔄 The Mount-Point Redirect Pattern

```
BEFORE MOUNT:
  /var/www/html/images/ → local disk (EBS)
  
AFTER MOUNT (EFS at /var/www/html/images/):
  /var/www/html/images/ → EFS (network shared storage)
  
  Apache reads /var/www/html/images/photo.jpg
    → transparently served from EFS
    → Apache doesn't know or care it's NFS
    → ALL instances see the same files
    
OPERATIONAL ORDER:
  1. Move existing files OUT of mount point
  2. Mount EFS at the path
  3. Copy files BACK into the (now EFS-backed) path
```

## 🧩 Reusable Engineering Patterns

```
PATTERN 1: SHARED STORAGE FOR STATELESS COMPUTE TIER
  Compute instances = stateless (replaceable, scalable)
  Shared files = centralized storage (EFS/NFS/S3)
  → Same as: Kubernetes shared PVCs, NFS in on-prem clusters,
    GlusterFS, CephFS, S3 for static assets

PATTERN 2: SECURITY GROUP CHAINING (SG → SG)
  Service SG allows traffic FROM compute SG (not IP-based)
  → Auto-scales: add/remove instances → access auto-adjusts
  → Same as: K8s NetworkPolicy label selectors,
    service mesh authorization, IAM role-based access

PATTERN 3: MOUNT-POINT REDIRECTION (Transparent Storage Swap)
  Mount network storage at application's data directory
  → Application is unaware of storage change
  → Same as: Docker volume mounts, K8s PVC mounts,
    NFS mounts in any Linux system, bind mounts

PATTERN 4: BAKE CONFIGURATION INTO IMAGE (AMI with fstab)
  Configure once → create AMI → all future instances pre-configured
  → Same as: Docker image with config baked in,
    golden image pipeline, Packer builds,
    immutable infrastructure pattern

PATTERN 5: MOVE-MOUNT-RESTORE (Safe Storage Migration)
  Move data out → mount new storage → copy data back
  → Standard procedure for ANY storage migration
  → Same as: database migration to new disk,
    moving logs to dedicated volume, NFS mount replacement
```
